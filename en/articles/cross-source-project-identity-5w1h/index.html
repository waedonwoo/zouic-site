The same board on five platforms: deduplicate by project or list by source

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

The five sources ZouIC aggregates are not five pages of the same kind: GitHub is a repository, Hackster.io a project tutorial, CrowdSupply a crowdfunding product page, Hackaday a news write-up, and Seeed Studio a vendor product page. One and the same development board — even one and the same open-source project — often has a differently shaped page in each of these five places. Index design therefore runs into a question that has to be answered first: are they one record or five? Listing by source produces five near-identical cards in the results; deduplicating by project can merge v1 with v2, or the original author’s board with someone else’s compatible implementation, into a single entry. The 5W1H breakdown follows. Conclusion first: the identity key is hardware entity plus version plus original author, and source hangs below it only as a document-type dimension; the platform name must not be the key, and deduplication cannot rely on title similarity.

What: what is treated as duplication is actually four different relations

At least four relations hold among the five pages. The first is different entry points to the same project: repository, tutorial and news write-up all point at the one board the author built themselves, so the identity is the same. The second is derivation: someone made a revision, a port or a compatible board based on the original, so the new work relates to the original but is not the same thing. The third is different revisions of the same hardware: v1 and v2 have similar names and look alike, but their pinouts, part numbers or firmware are not interchangeable. The fourth is different descriptive framings of the same product: a vendor specification page and a third-party review describe the same item, yet the parameters may differ because the measurement conditions differ. Call all four relations “duplicates” and the deduplication rule can only guess by title or image similarity, which either misses merges or makes wrong ones. The schema.org vocabulary happens to supply the language to tell them apart: sameAs for a reference page that unambiguously points at the same identity, isBasedOn for derivation and adaptation, exampleOfWork and workExample for instances and implementations, and citation for reference. Fix the relation type first; only then does deduplication make sense.

Why: two different cost curves

The cost of listing by source is visible: more index entries, more static export pages, a longer sitemap, near-duplicate hits in site search, and readers having to judge for themselves which copy is authoritative. The cost of deduplicating by project is hidden: once a merge is wrong, the error enters every downstream decision — whose parameters the card takes, which licence it follows, which original link it points at, how the multilingual versions correspond, and whether the machine-readable list counts one entry or five. The Google Search Central canonicalisation documentation adds two constraints: rel=canonical is a hint, not a rule, and the platform may choose a different canonical URL; and different language versions of the same content count as duplicate pages only when the main content is still in the same language. That means deduplication cannot be achieved by pointing canonical tags among the five pages, nor by compressing the trilingual cards into one canonical address. The genuinely controllable approach is to fix identity in the site’s own data layer first and then let the page layer’s links and markup express that identity, rather than expecting an external platform to guess on the site’s behalf.

Who: who is entitled to define “the same project”

The original author is best placed to decide, usually delimiting a project by repository name, version number, hardware revision or project homepage; a vendor delimits a product by model and SKU; a crowdfunding platform delimits one batch of deliveries by a single campaign; the media delimit one event by one article; and an aggregation site has no right to define, only the right to record and to merge. These five identifier schemes do not convert into one another naturally: one repository may map to several product models, one campaign may spawn two repositories, and one article may mention three boards at once. The site should therefore not invent a “global project ID” that overrides every source; it should keep each source’s own identifier and record one separate merge decision of its own, with the basis and the date written down. Machine readers matter too: whichever page sameAs points at is the identity the site asserts to the outside; if it points at a vendor product page while the card describes an open-source repository, the assertion is inaccurate. Storing the merge decision apart from the source identifiers means that, when a decision later turns out wrong, what changes is one relation rather than a full rewrite of the table.

When: merging happens at inclusion, review happens when a source changes

The merge decision should be made once at inclusion with its basis recorded, not recomputed by an algorithm on every export — recomputation lets the same card’s ownership shift quietly after some build, and historical versions of a static site stop being comparable. Later reviews are triggered by three kinds of event: a new version or revision appears, a source page changes its model or licence, or the original author moves the project to a new address. Trilingual versions add another time offset: a translated card may not be included or updated on the same day as the Chinese one, and aligning language versions by “identical title” easily mismatches the pre- and post-revision pair. Google’s documentation on language versions supports this approach too: pages count as duplicates only when the main content is still in the same language, so each of the three languages should self-reference a canonical and use a closed hreflang loop for the correspondence, rather than setting one of them as the canonical address for the others. Every change to a merge decision should keep a date and a reason, because “why it was merged at the time” is harder to reconstruct than “whether it is merged now”.

Where: one master record, many source slots, each with its type stated

The data layer builds one master project record whose fields are the hardware entity name, version or revision number, original author or maintaining body, and the site’s merge basis and date; each source hangs below it as a separate slot with at least the platform, the original URL, the document type (repository, tutorial, crowdfunding, news write-up, vendor specification), the identifier that source uses, and inclusion and check dates. The page layer groups sources by type so a reader sees at a glance where the code is, where to get started, where to buy and who covered it, rather than five flat, similar links. The structured-data layer points sameAs only at the one reference page that unambiguously establishes identity, and uses citation or an ordinary link for the rest; derivative projects get their own record linked with isBasedOn. The machine-readable layer and the sitemap list only the addresses of the site’s own master records, and source pages do not enter the site’s list. That way, even if one source is taken down later, only one slot is removed and the master record, the trilingual correspondences and the list scope all stay untouched.

How: make merging a five-step reviewable process

Step one, at inclusion fill the source slots first and do not rush to merge; each slot keeps that source’s own model or repository name. Step two, decide identity: only when the hardware entity, the version or revision number, and the original author all match is something treated as the same project; if any one is missing, mark it “pending” and do not merge automatically. Step three, decide the relation: identical identity goes into the same master record, a derivative or revision gets a separate record linked with isBasedOn, and different descriptions of the same product go under one slot type with the difference in framing labelled. Step four, designate the single identity reference page for sameAs, arrange the remaining source links by document type, and let the trilingual cards each self-reference a canonical and form a closed hreflang loop. Step five, before export run assertions: no two slots of the same type on the same platform under one master record, exactly one identity reference page per master record, no duplicate addresses in the sitemap, and differences in parameter framing explicitly labelled rather than silently averaged. All five steps keep a date and a basis, so a merge error can be caught at the next check instead of being frozen in by the next export.

Boundaries: what this identity framing does not cover

It cannot settle whose parameters are more trustworthy. When a vendor specification page and a third-party review give different values, all the site can do is set the sources and measurement conditions side by side; it cannot pick a “correct value” for the reader, still less average them. Nor does it govern licensing: the code, schematics and documentation of one board may fall under different licences, and merging them into one master record is not the same as merging them into one authorisation. The schema.org fields are vocabulary definitions and do not guarantee that any platform reads them as the site expects; rel=canonical is, per platform documentation, only a hint and cannot force an external party to adopt a given canonical URL. Another common misjudgment comes from naming: compatible boards, clones and teaching variants often reuse similar names, so deduplication by string similarity is almost bound to go wrong. Finally, static export and caching let pages from different moments coexist outside the site, and no matter how clearly the identity framing is written, it cannot guarantee that the version in a reader’s hands is the latest — only a baseline date and a check date can mitigate that.

Conclusion: fix identity first, then talk about deduplication

“Deduplicate by project or list by source” is a false either-or, because the two answer different questions: identity is the key of the master record, source is a document dimension hanging below it. Take the platform name out of the key and use hardware entity plus version plus original author instead, and store the merge basis and date explicitly; source slots keep their own model, type and check date and never have their parameters merged silently. Structured data puts only the genuine identity reference page into sameAs, leaves derivation to isBasedOn, and aligns trilingual versions through self-referencing canonical and a closed hreflang loop. A card like this answers both “what is this” and “where is the code, where is the tutorial, where can it be bought, who set the licence”, and readers no longer have to guess which of five near-identical results is the real one.

Frequently asked questions

If the same board has pages on five platforms, why not keep just one link?

Because the five page types serve different purposes: the repository gives code and design files, the tutorial gives getting-started steps, the crowdfunding page gives delivery information, the news write-up gives background, and the vendor page gives specifications. Keeping only one makes readers lose the other four entry points. What the site should do is list sources by document type under one master record, not compress five pages into a single URL.

Where is the risk in automatic deduplication by title similarity?

The risk concentrates on revisions and derivatives: v1 and v2, an original and a compatible board, a clone and a teaching variant often keep highly similar names. The test used here requires the hardware entity, the version or revision number, and the original author all to match; if any one is missing, mark it as pending and do not merge automatically.

Can canonical tags pointing among the trilingual cards be used to deduplicate them?

They should not be. Per Google’s documentation, pages count as duplicates only when the main content is still in the same language; each of the three languages is complete content in a different language. The correct approach is for each card to self-reference a canonical and use a closed hreflang loop for the correspondence, leaving identity consistency to the master record in the data layer.
