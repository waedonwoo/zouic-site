What a page should show when the translation has not caught up

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

Some time after a multilingual site goes live, a line or two of Chinese will occasionally surface on the English and German pages. The cause is almost never a translation that was overlooked; it is the seemingly safe fallback written into the template: if a translation key cannot be found, use the Chinese default value in the template. Nothing throws an error and the page still returns 200 — the reader simply meets another language on an English page. Below, the 5W1H lens takes apart “what the page should show when the translation has not caught up”. The conclusion first: a missing translation must be decided explicitly by the content manifest, never implicitly by a default value in the rendering layer; better to include one item less than to treat mixed languages as a compatibility strategy.

What: three places where Chinese leaks out

The first is the UI dictionary. Templates commonly use the pattern “look up a key, and if it is missing fall back to the Chinese text written into the template”; when a new feature adds only the Chinese template and nobody synchronises the English and German dictionaries, that default appears directly on the page — including text such as aria-label, placeholder and image alt that the eye does not catch at a glance but a screen reader reads aloud. The second is body translation. Multilingual sites often stack dictionaries in the order “base language, then English, then German”; the moment one layer lacks a key, it falls back to an earlier language, and in a long article aligned block by block, one missing block shifts every later block out of place. The third is full-text archive-type files: when they are assembled into the English or German version and the original text is pushed in despite having no translation, the language purity of the entire file is broken. What the three share is this: the fallback logic improves “not blank”, but quietly moves the decision about “which language” from the content side to the rendering side.

Why: language purity is a promise, not a cosmetic issue

A reader who enters a language version assumes that everything on that page belongs to that language; search and automated processing likewise treat page language as a signal. Mixed languages cost you on three levels: incoherence for the reader, misdetection for language detection, and ambiguity downstream about “which version is this page anyway”. Worse, it disguises itself as a normal state: the page renders, the status code is 200, the word count is adequate, and only a language-purity check exposes it. The check has its own traps — count Chinese characters across the whole HTML and Chinese comments in script and style blocks, Chinese text in template author cards and commented-out old copy all produce false positives; conversely, MarkupSafe escapes ASCII apostrophes and straight quotes into HTML entities, which a crude rule can mistake for an anomaly. So the metric “zero Chinese residue on English and German pages” first has to define exactly which text is being counted: usually the visible body after stripping script, style and HTML comments, plus metadata such as title, desc and aria-label.

Who: content, translation, templates and validation each carry their own responsibility

The content team decides which entries actually exist in a given language and owns the choice between “skip” and “keep a placeholder note”; the translation module handles block-by-block alignment across the title, description, keywords, frequently asked questions and every body block; templates are responsible for not emitting a Chinese default as a fallback on non-Chinese pages; and the validation script should turn coverage into a table before release rather than reporting a single total. The party most often missing from that split is the last one: without automated validation, readers tend to discover coverage gaps first. Another role that callers routinely overlook is the screen-reader user: a button’s aria-label, a search field’s placeholder and the alt of a QR-code image all sit on the edge of visibility checks — a human glance over the page will not see them, yet they genuinely belong to “what the page displays”. Bringing that text into the dictionary coverage check matters as much as finishing the body translation.

When: three update moments that do not line up

Source-text updates, translation updates and dictionary updates do not happen together: when a Chinese article changes its lead, the English and German translations may not follow that same day; when a new UI component ships, the UI dictionary may be filled for several languages at once or may go live in Chinese first. Coverage checks therefore cannot run only at “major releases”; they should be attached to every content or template change. The order in which languages are stacked also carries a time meaning: the base language is the default layer and English and German are override layers, so if a newly added key lands only in the Chinese template, the other two layers sit in a “will expose Chinese” window until they are filled in. The sound approach is to make that window visible in the release process — use the “missing-key list” as a gate before export, and forbid publishing the affected language while the list is non-empty — rather than fishing for problems with post-launch inspections. Quality review of the translations can run on a slower cadence, but coverage and block-count alignment must be verified live on every export.

Where: four kinds of landing point to verify separately

The first kind is visible body text and headings: check that text in the target language exists and that the block count matches the source. The second is metadata — title, description, keywords, H1, and names and contact details in structured data — which often reads from a separate dictionary, so finishing the body does not mean those are translated too. The third is accessibility text and UI controls — aria-label, placeholder, alt and button copy — the group most often left untranslated. The fourth is archive-type files: manifests, full-text files and the language versions of the sitemap, where the rule should be stricter — skip entries that have no translation in this language and state the filter rule in the file header rather than keeping an original-text placeholder. The shared source of truth for all four is the manifest of “which keys / which entries genuinely have a translation in this language”; the check script should compare against that manifest instead of relying on whether Chinese characters happen to appear on the page.

How: turn coverage into four executable rules

First: scan every lookup expression in the templates; any key whose fallback value is Chinese must also exist in both the English and German dictionaries, and set “zero missing keys” as the export gate. Second: align the body block by block and, article by article, compare the source against both languages for block count, number of FAQ entries, and the title and description fields; if any one differs, block the release, because a shifted block count throws every later passage out of sequence. Third: when measuring the language purity of visible text, strip script, style and HTML comments first, then check metadata such as title, desc and aria-label; put existing entity escaping and template author cards on the allowlist so false positives do not bury real problems. Fourth: generate archive files on an “include only where a translation exists” basis and state the scope and baseline date in the file header. What the four rules produce is a coverage table — how many body articles, how many UI keys and how many archive entries each language has, and where the gaps are — not a vague “trilingual support available”.

Boundaries: coverage checks cannot prove translation quality

Aligned block counts, a complete key set and no Chinese residue show only structural completeness and language purity; they do not show that the translation is accurate, the terminology consistent or the tone appropriate. Machine translation, word-for-word rendering and inconsistent technical terms all pass these four rules with ease. Conversely, a strict rule will also stop legitimate exceptions: brand names, a product’s official Chinese name, the original title of a regulation, code identifiers and quoted passages from another work may all legitimately put characters from another language on a page in one language, and these need an allowlist rather than a blanket rule. There is a further technical boundary: escaped entities and the difference between typographic and straight quotes add noise to character-based scanning, so the checking convention has to be fixed and written into the script or results will not be comparable from one run to the next. Finally, coverage and language signals are two separate systems: “hreflang all green” only means the version relationships hold, not that the text inside a given version really belongs to that language.

Conclusion: make missing translation an explicit decision

Turn “what exists in this language” into a manifest that templates and the export script only consume; a missing key no longer falls back to Chinese but fails a pre-release assertion; archive files would rather include less, yet state their scope in the header. Then bring visible text, metadata and accessibility text together into the language-purity check and list legitimate non-target-language exceptions on an allowlist. Only then is “trilingual support” a checkable claim: how many items each language covers, whether block counts align and whether any page mixes languages can all be computed on the spot. Translation quality still needs human review, but at least the avoidable mistake of “readers spotting leaked Chinese before we do” disappears.

Sources and framing (as of 12 November 2026): the dictionary stacking of “base language, then English, then German”, missing-key fallback to a Chinese default, article-by-article block alignment, counting Chinese characters only after stripping script and style, HTML entity escaping as a pre-existing phenomenon rather than a translation defect, and typographic quotes avoiding escape-related false positives, are all the site’s own multilingual-publishing engineering framing plus public technical roundups, and are not any platform specification. The bidirectional and self-referencing requirements of hreflang come from Google Search Central documentation; this article cites only their relationship semantics and does not conflate coverage checks with language signals. Third-party machine-translation quality and the language-detection behaviour of individual platforms have not been independently verified and are not used as a basis for conclusions; before implementing, defer to the actual behaviour of your own templates, dictionaries and export script.

Frequently asked questions

What is wrong with writing a Chinese default value into the template as a fallback?

It hands the language decision to the rendering layer. When the English or German dictionary is missing a key, the page simply shows Chinese, and the status code and word count still look normal; only a language-purity check catches it. Better to let a missing key fail an assertion before export instead of falling back silently.

To check English and German pages for Chinese, is searching for Chinese characters enough?

Not accurate enough. Chinese comments inside script and style blocks, HTML comments and template author cards all produce false positives; strip those parts out before counting visible text, check metadata such as title, desc and aria-label separately, and keep an allowlist for legitimate exceptions such as brand names.

For an article with no translation, can the original text be used as a placeholder?

Not recommended in archive-type files. An original-text placeholder breaks that file’s language purity and makes language-based automated processing judge it wrongly; the safer course is to skip it outright and state in the file header that content without a translation in this language is not included, together with the scope and baseline date.
