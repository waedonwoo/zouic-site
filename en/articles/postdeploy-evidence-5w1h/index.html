What evidence to keep after a release: what a live re-check should compare byte for byte

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

After a release someone on the team usually asks “is it up”. The quickest answer is to grep for the new copy and check that a few pages return 200. Both are fast and both are insufficient: a 200 only proves the address exists, while a keyword hit depends entirely on which word you chose. The project really did stumble once — after the services page shipped, searching for “session archive” returned nothing and for a while it looked as though the whole WeCom section had not rendered; the official product name is in fact “session content archive”, and the exported HTML had been compressed into a single line, so both the probe term and its presentation were wrong. Switching to block anchors and body text eventually revealed that seven product cards and two kinds of project-based products had been there all along. The 5W1H breakdown follows. Conclusion first: re-check evidence has three levels — existence, consistency and byte-for-byte identity; where a byte-for-byte comparison is possible, do not stop at keywords.

What: three levels of evidential strength that must not be mixed

The weakest is existence evidence: an address returns 200, key files can be fetched, a new entry appears in the sitemap. It answers “is it there”, not “is it this version”. In the middle is consistency evidence: checking a number of probes (block anchors, version numbers, stylesheet query parameters, structured data markers, language tags, statistics) against the local artefact item by item, answering “does it look right”. The strongest is byte-for-byte identity: extract the body text of the live page and the local artefact at the same path, remove noise and compare the strings, answering “is it the same content”. The three levels each have their cost, and byte-for-byte comparison is the slowest, but it covers most of the problems of the two earlier levels at once and is immune to a badly chosen probe term. Writing all three kinds of evidence into one sentence, “re-check passed”, effectively lets the weakest vouch for the strongest. The sound approach is to state plainly what was compared this time, how many pages, and with what result, rather than giving only a verdict.

Why: probes mislead, and so does the cache

Keyword re-checks have two inherent flaws: names change, since official product names, translation wording and rendered results of dynamic keys can all differ from internal shorthand; and HTML is compressed, escaped and injected with scripts, so a string you can grep by eye may not appear in the expected form. The cache creates a different misjudgement: request immediately after a push and you may get the previous version, in which case a probe not finding the new copy is normal rather than a failed deployment. The project’s handling is to wait out the deployment window, re-fetch with a no-cache parameter, inspect the last-modified time and cache status in the response headers, and only then decide between “not yet effective” and “genuinely wrong”. The GitHub Docs page on custom domains likewise notes that DNS changes can take a considerable time to propagate, so the site can only wait and re-verify. There is one more easily missed layer: the artefacts of a static site are the content of a public repository, and deleted files remain in version history, so “an old address is still reachable online” need not mean this deployment failed to delete it — a historical copy may still be serving it.

Who: the publisher, the host and the verification script each hold one part of the truth

The publisher holds the commit hash and the scope of this change, and knows what should appear; the hosting platform holds the build and distribution status, and knows when it actually takes effect; the verification script holds the external viewpoint, and knows what this request really returned. The three sets of information do not align automatically, and the most common accident is a publisher treating a local all-green as meaning live is already effective. The re-check record therefore has to link the three: commit hash, deployment wait time, request time and response headers, and which local artefact was compared. If release and re-check are carried out by different people, the expected change list should also be handed over explicitly, or the verifier can only pick probes from memory and falls back into the old keyword misjudgement. Once responsibility is divided clearly, the question “is it up” has a definite owner: it is not addressed to the platform, nor to the script, but to that evidence chain which can be re-checked.

When: four moments decide whether a re-check is valid

Push time supplies the commit hash and the change list; deployment time is decided by the platform and the site can only observe it; request time decides which version is returned and must line up with the deployment window; comparison time decides which file “local artefact” means, and if someone edits the source or re-exports in the meantime the baseline drifts. The project’s approach is to leave a deployment window after the push, then fetch the live page with a randomised parameter while recording the timestamps and cache information in the response headers; if necessary take a second sample later to confirm it was not an intermediate state of a cache switch. Of the four moments, comparison time is the one most often left out: many people write “live matches local” without saying which export local refers to. As soon as the source is edited in parallel, that sentence means nothing. Writing the four timestamps into the release record is worth more than running a few extra probes.

Where: compare the body text, not the whole HTML page

A full HTML page mixes in runtime injection, scripts, styles, comments, analytics code and possibly cache markers, so a byte-for-byte comparison of the whole page is almost bound to fail. The framing adopted in the project extracts the main body region, strips comments and script and style blocks, and then compares; this covers “is the content the same version” without being swamped by irrelevant differences. The concrete targets fall into three places: article pages compare the body text and language tags, services and pricing pages compare block anchors and structured data, and machine-readable text compares the whole plain-text content (files of that kind should contain no scripts anyway). Language versions must be sampled separately, because the three-language pages have different paths and different export mappings; comparing only the Chinese page misses problems on translated paths. Manifest-type files also need their statistics and baseline date compared separately, since those often appear in no page body at all yet are part of the outward promise. Choosing the right comparison scope is what makes byte-for-byte identity both strict and stable.

How: write the re-check as six steps and keep a record

Step one, fix the expected change list before release: which addresses, files, figures and baseline dates were added or changed. Step two, after the push record the commit hash and start waiting out the deployment window; do not conclude immediately. Step three, request key addresses with a no-cache parameter and record status codes and the timestamps and cache information in the response headers. Step four, run the live self-check list and archive its results alongside the two self-checks from before release. Step five, sample byte-for-byte comparisons: pick representative pages from the change list, extract their body text and compare it with the local artefact at the same path, sampling each language version separately; compare plain-text files in full. Step six, write the release record: the four moments, which pages were compared, against which local artefact, the result, and anything left uncovered. If any step looks abnormal, first distinguish the three cases “not yet effective”, “wrong probe” and “genuinely wrong”, then decide whether to wait, change the evidential strength or roll back; never let one failed keyword trigger a rollback directly.

Boundaries: what even byte-for-byte identity cannot prove

It cannot prove factual accuracy, sound framing or reliable third-party figures; those belong to content review. It cannot prove how external platforms interpret markers and manifests, nor how search results or AI answers will present things. It cannot prove which version the reader holds: browser caches, CDN edge nodes and machine clients that fetched the content weeks ago may all hold earlier copies. Sampling also has a natural coverage ceiling, and pages not sampled may still have problems, so the record must state the sampling scope rather than vaguely claiming “the whole site matches”. Finally, as GitHub Docs reminds, the artefacts of a public repository are public in themselves and deleted files remain in version history, so before release there should also be a check for “what should not appear in the artefact” — secrets, internal paths and debug information; these risks have nothing to do with byte-for-byte identity, yet they are just as much a part of release evidence.

Conclusion: keep a record that answers what it was compared against

The question “is it up” deserves a sturdier answer than “I found it”. Fix the re-check at three levels: first existence, then probe consistency, and finally sampled byte-for-byte comparison of body text; at each level state what was compared, how much, and against which local artefact. File the four moments, the commit hash, the response headers and the sampling scope together, and when something is abnormal first tell apart cache, probe and real defect. Then, even if someone looks back at this release years later, they can reconstruct the basis of the judgement from the record instead of finding only a subjectless “re-check passed”. One more point: the phrase byte-for-byte identical is worth keeping because it changes the question from “I think it shipped” to “these two things really are the same”.

Sources and framing (as of 13 November 2026): that the live services page once returned nothing for the probe “session archive” while the official product name is “session content archive” and the exported HTML is a compressed single line; that live re-check covers declaration effectiveness, the state of the three-language machine-readable text, the number of self-check items, the number of block products, stylesheet version parameters, and sampled three-language body texts of several articles compared byte-for-byte with the local artefact; and re-fetching with a no-cache parameter plus reading response-header time and cache status — all of this comes from ZouIC’s own release records and is the site’s own framing. The statements that DNS changes for a custom domain can take a considerable time to propagate and that a Pages repository is public with deleted files remaining in version history come from the official GitHub Docs and are official platform statements. Third-party write-ups on CDN caching and deployment latency are cited only as directional context and are not written into the conclusion; the site’s self-check results and platform behaviour are set side by side without being merged or averaged, and do not substitute for one another.

Frequently asked questions

If the new copy cannot be found online, can we conclude straight away that it did not ship?

No. First rule out three possibilities: the deployment window has not elapsed or the cache still holds the old version; the probe term differs from the official name or the translation wording; and HTML was compressed or escaped so the string appears in a different form. Switch to block anchors and a byte-for-byte comparison of the body text, check the response-header time, and only then conclude.

Why does byte-for-byte comparison cover only the body text and not the whole HTML page?

A whole page contains runtime injection, scripts, styles, comments and analytics code; those differences have nothing to do with whether the content is the same version and would make the comparison almost bound to fail. Extracting the body text and stripping comments and script and style blocks covers content consistency and stays stable; plain-text files can be compared in full.

If a sampled comparison passes, can we write “the whole site matches”?

Not advisable. Sampling has a natural coverage ceiling and pages not sampled may still have problems. The record should state the sampling scope, which local artefact was compared, the four moments and the result, using a re-checkable phrasing such as “several pages compared byte for byte”, rather than a sweeping whole-site conclusion.
