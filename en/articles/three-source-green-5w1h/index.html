Render, build and live source: three all-green results are not the same thing

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

The AI-readiness self-check on ZouIC supports three data sources: render renders pages in real time through the Flask test_client, build reads the exported static files, and live requests the deployed site. Run the same checklist against all three and every run can come back all green — every check passing. The trouble lies precisely there: three green results answer three different questions. A green render result says the templates, multilingual dictionaries, runtime configuration and routes are wired together correctly; a green build result says the exported artefacts, language path mapping and file assembly are correct; a green live result says that what outsiders actually receive after deployment is correct. No single green result can stand in for the other two, and none proves that source and artefact are the same version. The 5W1H breakdown follows. Conclusion first: the three sources must report separately and keep separate records, and the phrase “checks passed” must carry with it the source it was measured against.

What: two conversions stand between the three sources

From source code to reader, content passes through two conversions. The first is export: the application derives hundreds or thousands of static addresses from routes and languages, writes multilingual pages into a directory structure, and at the same time generates sitemap shards, robots, llms text and structured data. This step introduces path mapping, bulk cleanup, encoding and line endings, and the question of which derived paths do not actually exist. The second is deployment: after the artefacts are committed and pushed, the hosting platform builds and distributes them, and through the CDN and caches an external request may receive a version that is several minutes old or older still. The render source sees the state before the first conversion, the build source sees it after the first and before the second, and the live source sees it after both. Any environmental difference at any intermediate step produces the situation where all three are correct yet differ from one another: for example, if the machine-readable text is generated on its own without carrying the monitoring address from the runtime configuration, the file will be missing an entire section of observation-endpoint notes; or if writing the file swaps line endings for another kind, the content has not changed by a single character yet the repository reports the whole file as changed.

Why: the checker is itself part of what is being tested

A more subtle reason is that the three sources share one checklist but fetch data in different ways, so the checker itself becomes a new variable. This actually happened in the project: the build source reported 404 for the services page and the pricing page although both files plainly existed, because the fetch function treated a trailing-slash directory as a file path and never appended index.html. Neither the files nor the export were wrong; what was wrong was the checker’s path resolution under the static source. The reverse holds too: the render source can compute ledger figures in real time, while the static source can only read text that has already been written down; if those few files are not refreshed after export, the numbers on the two sides diverge without either side raising an error. Problems of this kind never appear as a “failed item”; they appear as the checker implementation happening to bypass a real defect. Running the three sources side by side is therefore not redundancy, but a way of letting one checklist cross-validate itself across three fetch paths: one source passing while another fails is often more worth looking at than all three passing.

Who: four stages, and a different party responsible for each

The people who write templates and multilingual dictionaries care about the render source, because that is the layer they can change directly; the people who write the export script care about the build source, because path mapping, cleanup thresholds and encoding all happen there; the person responsible for release cares about the live source, because the commit hash, deployment window and cache headers live there; and the people maintaining the check script are accountable for each of the three fetchers separately, since a mistake in any one parsing logic produces a misleading green light. The hosting platform is a fifth party: its build and distribution behaviour is not in the site’s code, and the GitHub Docs page on custom domains warns that DNS changes can take a considerable time to propagate, so what the site can do is wait and re-verify rather than assume a push takes effect immediately. Writing “checks passed” into a commit message without naming the source compresses four parties of responsibility into one subjectless sentence, and when something goes wrong everyone assumes someone else verified it.

When: every green result carries a timestamp and expires

A green render result belongs to the source code in the current working tree and expires the moment that code changes; a green build result belongs to one export snapshot, and if the source is edited in parallel that snapshot diverges from it immediately; a green live result belongs to the online version at the moment of that request, and the deployment queue, CDN caches and later pushes all invalidate it. The project did run into a case where the source was edited in parallel during export: the artefact was a snapshot several hours old and the homepage had gained an unreviewed card, so the choice was to align the source first and re-export rather than publish the stale snapshot. Every self-check record therefore needs at least four times: the moment of the check, the corresponding source state, the corresponding export batch, and the corresponding commit hash. Re-verification after deployment also has to distinguish explicitly between “not yet effective” and “genuinely wrong”: re-fetching with a no-cache parameter and reading the last-modified time and cache age in the response headers says more than reloading the page over and over. Treating a green light as a permanent state is the most common time illusion in a release process.

Where: what each source checks, and why they must not stand in for one another

The render source is suited to semantics: whether routes return 200, whether multilingual keys are complete, whether other languages have leaked into visible body text, whether structured data types and fields are all present, and whether the six-dimension headings and the FAQ are rendered. The build source is suited to artefacts: directory and trailing-slash mapping, whether each of the three language paths exists on its own, whether addresses inside sitemap shards have corresponding files, whether there are duplicates and dead links, whether baseline dates and statistics in text files have been refreshed, and whether pages contain untranslated placeholders. The live source is suited to delivery: status codes, response headers and caching, whether key files match the local artefacts, whether sampled body text matches byte for byte, and whether the change tied to the commit hash actually appears online. Some checks belong to only one source: “whether runtime configuration was injected” can only be checked on the render side, “whether line endings were rewritten” only shows up on the build side, and “whether an old version is still in the cache” is only visible on the live side. The checklist can be shared; the conclusions cannot be merged.

How: turn the three sources into a timestamped evidence chain

Step one, run the render source before export and record the current source state together with any uncommitted changes. Step two, after export confirm that source and snapshot agree; if source was edited in parallel, re-export rather than relying on “we will fix it next time”. Step three, run the build source and at the same time validate the fetcher itself: a trailing-slash directory resolves to index.html, the language path mapping matches the real directories, and the three-language text files really were generated in this run. Step four, after committing and pushing, wait out the deployment window, run the live source with a no-cache parameter and an explicit User-agent, and record the timestamps and cache information in the response headers. Step five, perform one cross-source byte-for-byte comparison: extract the body text of a few pages, compare it with the local artefact at the same path, and write the result into the release record. Step six, report and archive the three sets of results separately, and never allow a non-green result in one set to be offset by green lights from the other two. What makes the whole process work is not the number of checks but that every green light can answer which version was measured, when it was measured, and what it was compared against.

Boundaries: what all three sources being green still cannot prove

It cannot prove that the content itself is right: whether facts are stale, whether framings contradict each other, whether third-party figures have been misquoted — the script does not judge that. It cannot prove how external platforms interpret machine-readable text, since who adopts structured data and extension directives, and how, is not the site’s decision. Nor can it prove which version the reader holds: the CDN, browser caches and machine clients that fetched the content weeks ago may all be holding an earlier copy. As GitHub Docs reminds, the content of a Pages repository is public and deleted files remain in version history, so the release process also needs a check for “what should not appear in the artefact” — secrets, internal paths and debug information — a class of problem the self-check checklist usually does not cover. Finally, the checker itself may have bugs, and a checklist shared by three sources copies the same blind spot three times over; periodically disproving the checker with manual sampling and cross-source byte-for-byte comparison does more good than endlessly adding checks.

Conclusion: report each source separately before asking whether to ship

Collapsing three green results into one sentence, “checks passed”, saves a line of log and throws away an entire evidence chain. The release record should always contain three fixed sections: how many items render passed, how many build passed, how many live passed, each with its source state, export batch, commit hash and check time; plus one section for the cross-source byte-for-byte comparison, stating which pages were compared and against which local file. Only then does the question “are we ready to ship” have something to stand on — the self-check answers “is it correct”, while release is a separate decision that needs someone to look at this evidence chain and make the call. Three green results are a necessary condition, not a sufficient one; losing sight of that is most likely to cause trouble on the day the source is edited in parallel, or the day the checker itself is written wrong.

Sources and framing (as of 13 November 2026): that the self-check script supports three sources render / build / live, the number of checks, the build source once reporting a false 404 because a trailing-slash directory was not resolved to index.html, a snapshot diverging because the source was edited in parallel during export, a missing section when machine-readable text was generated without the monitoring address, and a whole-file change with no content change caused by line-ending differences — all of this comes from ZouIC’s own engineering records and script implementation and is the site’s own framing. The statements that DNS changes for a custom domain can take a considerable time to propagate and that the content of a Pages repository is public with deleted files remaining in version history come from the official GitHub Docs and are official platform statements. Third-party write-ups on CDN and deployment latency for static hosting are cited only as directional context and are not written into the conclusion; platform behaviour and the site’s self-check results are set side by side without being merged or averaged, and do not substitute for one another.

Frequently asked questions

If render and build both come back all green, can the live re-check be skipped?

Not advisable. Both run before deployment and cannot cover the build queue, CDN caches, response headers or leftover old versions. The practice in this project is to wait out the deployment window after the push, then run the live source once more and do a byte-for-byte comparison of body text, confirming that outsiders really receive this version.

The static source reports 404 although the files plainly exist — where is the problem?

Most likely in the checker, not the artefact. This actually happened in the project: the fetch function did not handle a trailing-slash directory and never appended index.html to the path. A false alarm of this kind shows that when three sources share one checklist, the fetcher itself must be validated too; otherwise neither a green nor a red light can be trusted.

Why does refreshing machine-readable text show a whole-file change even though the content did not change?

Usually the line endings were rewritten. If there is no substantive content change, restore that file so a meaningless change is not committed to the repository; but first confirm that the counts, the baseline date and the configuration-injection section really match the current source, because restoring is not appropriate in every case.
