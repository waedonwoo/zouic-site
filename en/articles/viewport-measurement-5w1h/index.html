Who to trust at 390px: screenshot width, CSS pixels and real-device framing

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

A mobile review in the project set the headless browser window to 390 wide; the screenshot looked as though the whole page overflowed, and a version of perfectly fine styles was nearly changed. It later turned out the browser had clamped the window to a wider value, and the cropped 390 was only the image width, not the page actual layout width. Switching to a forced device pixel ratio with a multiplied window size, then reading the real value once with an in-page probe, finally produced a trustworthy 390 CSS pixels. This kind of misjudgement does not come from wrong CSS but from treating four different widths as one. The 5W1H breakdown follows. Conclusion first: a screenshot is visual evidence, not width evidence; every mobile review must read the actual value once inside the page and write the measurement framing into the record.

What: four quantities that all go by the name of width

The first is the window argument, a startup value handed to the browser process that may be rewritten by a minimum window size, system scaling or the window manager. The second is the CSS viewport width, the width layout and media queries actually use, in CSS pixels. The third is physical pixels, equal to CSS pixels multiplied by the device pixel ratio, so the same screen can hold several times as many physical pixels at high density. The fourth is the screenshot crop width, merely the pixel size of the output image, with no necessary relation to the width the page laid out at. The MDN viewport documentation spells out the key mechanics: when initial or maximum scale is set, width actually behaves as a minimum viewport width, and the browser expands the viewport to fill the screen when needed; on high-density screens several hardware pixels map to one CSS pixel, the devicePixelRatio default varies with screen density, and the default ratio holds only at zoom 1; without a suitable viewport declaration some browsers adopt a virtual viewport of about 980 CSS pixels and scale it, so narrow-screen media queries never fire at all. Mix the four up and the conclusion is bound to drift.

Why: false breaks and false passes come from the same mistake

Treating the window argument as the CSS viewport gives a false break: you think there is overflow at 390, when in fact the page laid out wider and the image, cropped narrow, naturally looks as though content is cut off. The reverse, treating a screenshot that looks fine as a pass, gives a false pass: the image may have been magnified by the device pixel ratio, may have been scaled, or the target breakpoint may simply never have fired. The fix path in the project illustrates the point: rather than guessing by adjusting the window argument again, put a probe in the page to read innerWidth and devicePixelRatio, retest with a fixed-width iframe if needed, and turn current layout width into a printable number. MDN also flags two further kinds of interference: browser zoom changes the CSS viewport width, and interactive components such as a virtual keyboard change the viewport too, with interactive-widget controlling whether the visual or the layout viewport is affected. All of this says width is not a constant a startup argument can decide on its own, but a runtime state.

Who: the browser, the page, the mini program and the review script each decide their own part

The browser decides window clamping, zoom, the virtual viewport and the device pixel ratio; the viewport declaration in the page itself decides how the layout viewport is computed; the mini program is an entirely separate system, with the WeChat open documentation fixing page width at 750rpx and the platform converting it into real dimensions by device model, so the main site CSS pixel values cannot be applied directly. The review script decides the sampling method: whether it reads an in-page probe or only looks at the output image; the human reviewer decides whether looking right was taken for having measured. Of the four parties, the only one that can give an authoritative number is the in-page probe, because it reads exactly the CSS pixels layout used. Once this layer is separated, the discussion shifts from “does the screenshot look right” to “what was measured this time, by whom, and with what number” — which is the kind of sentence that belongs in a verification record.

When: three sampling moments, and missing one can mean a misjudgement

The first is at page load completion: the layout viewport is settled and it is a good moment to read innerWidth and devicePixelRatio. The second is after fonts, images and script execution have stabilised: asynchronous content can change scroll width or trigger horizontal overflow, so an early screenshot misses a real break. The third is after an interaction state changes: a virtual keyboard appearing, a screen rotation or a zoom change all alter the viewport, and verifying those scenarios means sampling them separately. The project used a virtual time budget to wait for rendering to settle, then took a full-page screenshot plus local crops, precisely to separate the first two moments. Caching and versions form a time dimension too: which version of the page a screenshot corresponds to must be traceable to a commit or an export batch, or the same image cannot be explained a few days later. Writing the three moments into the record together with the target version is far more useful than keeping a pile of images without metadata.

Where: numbers in the record, images in the attachments, conclusions at the breakpoint

The verification record should state the target CSS viewport width, the innerWidth actually read, devicePixelRatio, the window startup argument, the zoom setting, the page version and the sampling moment; these are reproducible numbers. Screenshots are visual attachments only, for seeing overlap, misalignment and overflow, and carry no burden of proving width. The conclusion lands at the breakpoint: which media queries fire at the target width, whether the layout is single-column, whether navigation collapses, whether there is horizontal scrolling. Multi-end cases are recorded separately: the main site in CSS pixels and media queries, the mini program in rpx and platform conversion, and neither record borrows numbers from the other. If a fixed-width iframe is used as the probe, note that this is container width rather than browser window width, so the next person does not equate the two. Keeping the three layers apart is what stops a screenshot being mistaken for a measurement report.

How: make mobile review five steps, each leaving a number behind

Step one, fix the target: which CSS viewport width is being verified and which breakpoint it corresponds to, not roughly how wide a phone is. Step two, launch the browser in a way that actually produces the target CSS width: if needed use a forced device pixel ratio with a multiplied window size, or switch to a fixed-width iframe, and do not expect the window argument to equal the layout width. Step three, have the in-page probe print innerWidth, devicePixelRatio and scroll width, confirm the actual value matches the target, and if it does not, fix the measurement method first rather than the styles. Step four, wait for rendering to settle before screenshotting, then check overlap, overflow and collapse; sample interaction scenarios separately. Step five, write the record: target value, actual value, startup argument, zoom, page version, sampling moment, screenshot path and conclusion. If a break shows up at any step, first confirm it is not a measurement error, then touch the CSS. The core of these five steps is not the tool but replacing “I saw it” with “I measured this much, by which framing”.

Boundaries: measuring correctly still does not mean the real device is fine

A headless browser measuring 390 CSS pixels only says this layout width matches the target; it cannot reproduce real-device font rendering, system scaling, browser chrome occupation, notches and safe areas, touch-target feel, or the small differences between vendors in viewport and virtual-keyboard behaviour. The MDN documentation itself lists the three values of interactive-widget as distinct behaviours, which shows viewport change has an interaction dimension too. The rpx system of the mini program is converted by the platform, so simulated values in a desktop browser cannot stand in for actual behaviour inside the platform. This kind of review should therefore be framed as a layout check after measurement error has been excluded, with on-device preview and sampling on the device remaining separate steps. A screenshot also covers only the visible area captured; breakage in the lower half of a long page needs a taller viewport or segmented sampling, and a normal upper half does not prove the whole page is normal.

Conclusion: write the measurement framing into the verification record

The most valuable thing in a mobile review is not the screenshot but the line of numbers beside it: what the target was, what was actually read, by which method, and which version was measured. The “390 full-screen overflow” scare in the project cost only one extra run; had the styles been changed on the strength of that false break, the real breakpoint problem would have been masked instead. Make four things a fixed routine: printing the probe, waiting for rendering to settle, filing numbers and images separately, and landing the conclusion at the breakpoint, and keep main site CSS pixels and mini program rpx explicitly as two framings. Then the next time someone says “it looks wrong on a phone”, the first answer is not “my screenshot is fine here” but “first tell me the innerWidth you measured”.

Sources and framing (as of 13 November 2026): that the headless browser clamped a 390 window argument to a wider value, that the cropped 390 was only the image width, and that switching to a forced device pixel ratio with a multiplied window size and re-checking with an in-page iframe probe produced the right value all come from ZouIC site-internal visual review records and count as site-internal framing. That width behaves as a minimum viewport width when initial / maximum scale is set, that the browser can expand the viewport to fill the screen, that CSS pixels and hardware pixels convert through devicePixelRatio, that the default pixel ratio is tiered by screen density and holds only at zoom 1, that a missing viewport declaration yields a virtual viewport of about 980 CSS pixels, the three values of interactive-widget, and the specification reference CSS Viewport Module Level 1 all come from the MDN Web Docs viewport documentation and count as authoritative documentation and specification framing. That rpx takes 750rpx as the page-width basis and is converted by the platform comes from the WeChat open documentation and is official platform framing. Third-party viewport test tools and breakpoint experience articles are cited only directionally and are not written into the conclusion; browser-simulated values and real-device behaviour are set side by side and do not replace each other.

Frequently asked questions

I set the browser window to 390 — why is the layout not 390?

The window argument is only a startup value and may be rewritten by minimum window size or system scaling; and if the page sets initial or maximum scale, MDN notes that width actually behaves as a minimum viewport width, and the browser may expand the viewport. The innerWidth read by a probe inside the page is what counts.

The screenshot shows no overflow — can that count as a mobile pass?

Not on its own. The screenshot may have been magnified by devicePixelRatio or scaled, or the target breakpoint may never have fired. Print the actual CSS viewport width and devicePixelRatio first, confirm the measurement is right, then let the screenshot do the visual job of showing overlap, misalignment and overflow.

The main site measures 390 CSS pixels — can I infer the mini program behaviour from that?

No. The mini program works in rpx converted by the platform, with 750rpx as the page-width basis, which is a different framing from the main site CSS pixels and media queries. The two ends are sampled and recorded separately and neither record borrows numbers from the other; real-device preview remains a separate step.
