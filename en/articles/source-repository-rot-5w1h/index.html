When a source repository is deleted or archived: what an index card keeps and what it labels

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

Anyone running an aggregation site eventually meets this day: a project card that has been listed for half a year, whose source link opens to a 404. The instinct is to clear the dead link and make the sitemap and checks clean again. But “clearing” also erases something else — what the site originally relied on to list the project, on which day it last checked, and what happened afterwards. Official GitHub documentation distinguishes upstream states quite finely: archiving is read-only and signals no further active maintenance, deletion is irreversible and need not affect existing forks, and public content may also be made unavailable for compliance reasons. These states mean entirely different things for an index card, yet they are routinely flattened into a single available flag. The 5W1H breakdown follows. Conclusion first: a status needs a type, a date and a destination for its evidence; cleanup targets the site’s own addresses, not the external-link record.

What: breakage is not one state, but at least five

Per the official GitHub Docs description, archiving a repository makes it read-only for all users and signals that it is no longer actively maintained; after archiving, issues, pull requests, code, wiki, releases, commits, branches and permissions all become read-only, yet the repository stays searchable, forkable and star-able, and archiving can be undone. Deletion is a different matter: deleting a repository is irreversible, some deleted repositories can be restored within a limited window, deleting a public repository does not delete its existing public forks, and the platform selects one existing fork as the new parent so the network continues. Three further common changes exist: a licence file is replaced or added, a repository switches from public to private or back, and content is made unavailable following a DMCA notice or a terms violation. Recording all five changes as “the link no longer opens” leads straight to two errors: mistakenly removing an archived project that is still readable, and continuing to label a project under an old licence after its terms have changed.

Why: cleanup logic and evidence logic pull in opposite directions

The export script of a static site is naturally biased toward cleanup: the site’s own pagination, legacy directories and derived language paths all need periodic pruning, or the output grows without bound and the sitemap starts listing addresses that point at files that do not exist. The ZouIC export chain includes exactly this kind of batch cleanup, with a threshold guard so one mistake cannot wipe out dozens of directories at once; sitemap generation also proactively excludes derived language paths that do not exist. That logic applies only to the site’s own addresses. The external-link record belongs to evidence logic, whose aim is to let someone later reconstruct: what this project was at the time, why the site listed it, when a change was noticed, and whether an alternative entry exists. Mixing the two logics inside one “clean up dead links” task most commonly ends with a fully green check after a successful export while the basis for inclusion is gone for good. The machine-readable layer is trickier still: if the scope note in llms.txt or a list says “what the site currently lists”, deleting a broken card is honest; if it says “what the site has listed, with records kept”, deleting it becomes a broken promise.

Who: upstream, archivists, site and reader each hold their own copy

Upstream authors or maintainers decide archiving, deletion, licence changes and visibility changes, and usually do not notify downstream aggregation sites. The platform decides under what conditions content becomes unavailable and also provides long-term preservation: GitHub Docs states that the GitHub Archive Program covers all public repositories by default, cooperates with institutions such as the Software Heritage Foundation and the Internet Archive, and keeps copies in multiple formats and locations; the documentation also recommends adding an open-source licence, because explicit permission to copy and redistribute affects whether third parties are willing to archive a repository, and repository owners can opt out of the programme. The site decides how much state to keep and how to phrase it externally; the reader needs to know whether the project can still be obtained, where, and under which licence. The four parties hold asymmetric information: the platform knows what was deleted, an archive institution may still hold a copy, and the site knows only what its last check saw. The site should therefore not pretend to a global view; it should write down its own part honestly and phrase “a mirror or fork may still exist” as a hint, not a guarantee.

When: check date, change-discovery date and export date are three separate days

The inclusion date says when the project first entered the index; the last-checked date says when the site last successfully reached the source link, and proves only that “the link and fields were accessed that day”, not that the content was correct; the change-discovery date says when the site first observed a state change, and it usually lags behind the real upstream change — the lag cannot be removed, only labelled. Static export is a fourth moment: once the page is frozen into HTML it does not follow upstream automatically until the next re-export. Writing these four days into the card and internal records is what gives a traceable sequence when a dispute arises. Two calendar-like facts on the platform side deserve their own note: whether a deletion is still inside its restore window, and whether an archiving has been undone. They decide whether the site should “mark as pending review for now” or “relabel as restored”. No automated task should declare permanent breakage from a single failed request — network jitter, rate limiting and temporary maintenance all produce the same symptom. The safe approach is several spaced observations in a row before changing the state.

Where: status lands in the card, the record and the list, with different wording in each

What the reader gets on the card is one short status plus a date, for example “source repository archived, still readable read-only” or “source link unreachable, last checked on such-and-such a day”, with the original link and licence pointer kept; wording that would reshape the impression of authorisation, such as “backed up on this site” or “get a copy here”, is not written. The internal record holds the full state machine: archived, deleted, licence changed, visibility changed, alternative entry available, pending review, restored, plus the raw status code and time of every observation. Because machine-readable lists and the sitemap list only the site’s own addresses, an external-link failure should not trigger “remove the site’s card from the sitemap”; only a decision to take the whole card down handles both the site address and the list scope at once. If the site really does offer a mirror or archive reference, it must label the provider and the licence basis separately and must not conflate it with the source link. The three places use different wording but share one state, driven by a single internal status field, so the card does not say archived while the list says taken down and the record says 404.

How: write “what to keep” as a six-step status flow

Step one, persist at inclusion: source link, platform, licence pointer, inclusion date, the site’s own description and tags — nothing is accepted if one is missing. Step two, periodic checks read only the state and licence-file changes, not the body text, so the index does not turn into a cache. Step three, retry failures and grade them: distinguish a network error, a 404, a 403, a redirect to a different domain, and a page that is still there but whose licence file changed, and route each result into a different state. Step four, during the observation window mark the item “pending review”, keep the card and the original link, and neither delete it silently nor treat it as normal. Step five, once a change is confirmed, label it by type and spell out that “archived is not the same as unavailable”, “deleted is not the same as every copy gone”, and “a licence change follows the changed file, with historical labels kept but dated as superseded”. Step six, before export run two independent assertions: no dead links among the site’s own addresses, and complete external-link status fields in which every non-normal state has a date and an observation record. Splitting cleanup from retention into two tasks and reporting their counts separately in the check report is what stops one green run from hiding a blank layer.

Boundaries: what this state machine cannot answer

It cannot answer whether a licence actually permits a given use. Archiving says only something about maintenance status, not whether the licence still holds; a licence change may affect only later versions, and what governs historical versions has to be read from the specific files and commit history — this note makes no legal judgment on the original author’s behalf. A platform archive programme is a preservation mechanism, not an authorisation for the site to redistribute on that basis; the official documentation recommends adding an open-source licence precisely because of that distinction, and the site can only hint at, not guarantee, whether an accessible mirror or fork exists. One more lag cannot be engineered away: the static page, the CDN cache and an old version in a machine reader’s hands may all differ from today’s source site. As for content made unavailable for compliance reasons, the site should not even try to bypass or reconstruct it. Every question of this kind should land on one sentence — “defer to the original author’s and the platform’s current pages” — with the site’s own check records kept as facts, not as conclusions.

Conclusion: clean up site addresses, keep external-link evidence

Separating the two kinds of action cleanly is the least effortful solution here. Batch cleanup handles only the site’s own pagination, legacy directories and derived paths, and keeps the threshold guard plus a record that “skipping the guard requires a reason”; external-link failures enter the state machine with a type, a date, an observation record and a hint at an alternative entry, and the card stays readable but is no longer described as “currently available”. The state machine need not be elaborate — seven or eight values plus three dates are enough — the point is not to let one boolean stand in for every judgment. Then, when someone asks “why is this project still on the site”, the answer is not “we forgot to delete it” but “the source repository is archived, still readable read-only, last checked on such-and-such a day, original link kept” — one reviewable sentence is more useful than one clean, fully green check.

Sources and framing (as of 13 November 2026): that an archived repository is read-only and signals no further active maintenance; that issues and code become read-only and archiving can be undone; that deletion is irreversible, some deleted repositories can be restored within a limited window, and deleting a public repository does not delete its public forks; that public repositories persist, yet content may be made unavailable in DMCA or terms-violation cases; and that the GitHub Archive Program covers public repositories by default, cooperates with the Software Heritage Foundation and the Internet Archive, recommends adding an open-source licence so third parties will archive a repository, and lets owners opt out — all of this comes from the official GitHub Docs documentation and is official platform framing. The export script’s threshold guard for batch cleanup, its exclusion of derived language paths, and its sitemap dead-link check come from ZouIC’s own engineering records and are the site’s own statement. Third-party write-ups on link rot and archiving practice are cited only as supporting context and are not written into the conclusion; a platform preservation mechanism does not constitute a redistribution licence, and the two are set side by side here without drawing an inference.

Frequently asked questions

If a source repository is archived, should the card be taken down?

Usually not. Per GitHub Docs, archiving means the repository is no longer actively maintained and becomes read-only, while its content remains searchable, forkable and star-able. The card should be relabelled with the status and a date and keep the original link, rather than being deleted as broken. Taking a card down is a separate decision: it happens only when the site itself decides to stop listing the project.

If an external link returns 404, why is the retained card not counted as a dead link?

Dead-link checks target the site’s own addresses in the sitemap and lists; an external link is a reference inside a card and does not enter the site’s sitemap. It is kept to preserve the basis for inclusion and the check record, but it must be explicitly labelled “unreachable” with a last-checked date and must not look like a normally available source.

If a platform’s long-term archive programme includes the project, can the site offer a copy on that basis?

No licence can be inferred from that. GitHub Docs describes the archive programme as a preservation mechanism and recommends that projects add an open-source licence so third parties will archive them; whether a copy exists and whether it may be redistributed still depend on the original author’s licence and the platform’s current page. At most the site may hint that “a mirror or fork may exist” — it offers no copy and gives no guarantee.
