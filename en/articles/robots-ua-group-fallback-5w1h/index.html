Giving AI crawlers their own group removes them from the default rules

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

Giving each AI crawler its own User-agent group is the most natural step when a site refines its admission rules, and the easiest one to get wrong. Intuition says a dedicated group adds one exception on top of the wildcard group default; under RFC 9309 group matching, what actually happens is replacement: as soon as a crawler matches a group that names it, it reads only that group, and whatever is written in the wildcard group is irrelevant to it. The crawlers listed one by one therefore become precisely the clients least likely to see the site default declaration. The 5W1H breakdown follows. Conclusion first: a use declaration reaches only those whose group it is written into; a longer list is not the same as a stricter rule.

What: a group-matching rule that is consistently read backwards

RFC 9309 defines robots.txt as a set of groups, each beginning with one or more User-agent lines followed by Allow and Disallow rules, and ending when the next User-agent line starts a new group. The specification asks a crawler to find its matching groups using its product token with case-insensitive matching, and when several groups of the same name match, to merge their rules into a single group for parsing; only when it matches no dedicated group at all does it obey the asterisk wildcard group. A dedicated group, in other words, is not an exception but a complete substitute. The same mechanism has two consequences that are often overlooked. Within a group, the longest path match wins, with Allow taking precedence at equal length, and the order of lines does not decide priority — the opposite of the firewall instinct that the first matching rule takes effect. And an empty Disallow means no path is restricted at all, which is entirely different from Disallow: / blocking the whole site. Taken together, a file that writes one group per crawler and puts the blanket declaration in the wildcard group in fact reserves that declaration for the clients with no name.

Why: declaration and enforcement are mixed into one file

robots.txt was created to answer only which paths not to crawl, yet today it is asked to answer at the same time what may be done with content after it is taken. RFC 9309 states at the outset that these rules are not a form of access authorisation, and the Cloudflare developer documentation says plainly that compliance is voluntary: the file expresses a preference and cannot technically prevent crawling, so actually blocking requires enforcement at the edge or authentication layer. Use declarations (Content Signals, terms text) belong to the first category, bans and rate limits to the second. Once both are packed into the same plain-text file, an engineering illusion follows easily: that naming every crawler and writing a Disallow into each group also brings the uses under control. In reality a named crawler reads only the few lines in its dedicated group, and if that group holds a single Disallow, the entire declaration about uses simply does not exist for it. Worse, the file has its own reliability limits: the specification treats 4xx as no restrictions, 5xx and unreachability as a temporary whole-site ban, requires only the first 500 KiB to be read, and lets clients cache the file for up to 24 hours. A publishing incident here tends to do more damage than one mistyped business rule.

Who: four parties each write a section, nobody owns overall consistency

Standards bodies define the syntax and error semantics, site operators decide use preferences, an edge platform may host the file and prepend a block of its own managed content, and crawler operators decide whether and how to read it. The managed example in the Cloudflare developer documentation (updated 2 November 2026) stacks all four parties neatly: it prepends a block of managed content before the original robots.txt of the site, containing a User-agent: * group with Content-signal and Allow: /, followed by dedicated groups each carrying Disallow: / for Amazonbot, Applebot-Extended, Bytespider, CCBot, ClaudeBot, Google-Extended, GPTBot, meta-externalagent and others, and only then the original wildcard group of the site. This example is an official platform statement and must not be read as a mistake — the same platform enforces blocks at the edge through a separate crawler-control layer, and the Disallow in the file is only part of a preference sync. But it demonstrates one thing clearly: when a file is assembled by several parties, the assumption that every UA reads the same declaration does not hold, and the site must verify the final assembled full text itself rather than only the section it wrote.

When: three time scales that do not line up

The first layer is standards time. RFC 9309 is an IETF Standards Track document published in 2022, so group matching and error-handling semantics are relatively stable, whereas Content Signals is a policy text introduced by a platform in 2025, written into robots.txt comments and extension directives; it is not an RFC and its fields are still growing. Cloudflare documentation currently marks the fourth field, use, as an extension under testing, with three values — immediate, reference and full — and the managed content defaults to use=reference. The second layer is platform time: policy sync for managed robots.txt takes effect within seconds of saving, and the documentation explicitly says no cache purge is needed. The third is client time: crawlers may cache the file for up to 24 hours under the specification, their parsing implementations are not fully consistent, and Google Search Console may even report a new directive such as Content Signals as unrecognised syntax, with the platform documentation stating no observed effect on crawl rate. Treating a field under test, a platform default and a 24-hour cache as one single moment of being live is the most common source of misdiagnosis during troubleshooting.

Where: four locations whose boundaries do not overlap

Use preferences live in the comments and extension directives of robots.txt and belong to the declaration layer; path accessibility lives in Allow/Disallow rules and is a crawl instruction to compliant clients; actual allow, rate limiting and blocking live in the edge WAF, gateway or authentication layer and belong to enforcement; and what really happened lives in origin logs and ledgers and belongs to the fact layer. RFC 9309 also fixes the scope of the file itself: it is valid only for the host, protocol and port that serve it, so a subdomain, another protocol or another port each needs its own copy. One concrete engineering choice follows: if you do not intend to give different crawlers different path rules, do not open a group for each; keep a single wildcard group, put both the use declaration and the path rules inside it, and list the crawler roster as a comment at the top of the file for human review, so every client reads the same declaration. If dedicated groups are genuinely needed, accept that the declaration must be copied into every group, and encode every group has it as an automated check rather than relying on memory.

How: turn group matching into four reviewable steps

Step one: retrieve the full robots.txt text actually served to the outside as the single source of truth, rather than reading the template in the repository; when a platform prepends content, re-check the assembled result externally with a request carrying Cache-Control: no-cache. Step two: enumerate every User-agent line, compute for each product token, according to group-matching semantics, which group it actually reads, then check whether that group contains the use declaration and the necessary path rules; multiple groups with the same name must be evaluated on their merged rules, and longest-match precedence requires computing the length line by line. Step three: verify file reliability — a 200 status, a size well below 500 KiB, syntax accepted by the parser, and the publication time and version number of the two declaration files written into the log, so a 5xx is not silently read as a whole-site ban. Step four: make whether the declaration covers the target UA an assertion at release time, and keep a 24-hour crawl observation window on each side of a change, because old behaviour seen during the cache period is not a regression. Only after these four steps does a discussion of charging or blocking have a verifiable baseline.

Boundaries: where this decomposition stops holding

Group-matching semantics bind only clients willing to honour the REP and have no effect on fetchers that never read the file; a use declaration does not even reach the question of compliance, because it expresses a preference and a reservation of rights rather than a technical gate. The specification does not define extension directives such as Content-signal or use, and implementations differ on whether to ignore, reject or log them, so “written in the file” must not be equated with “received by the other side”. A platform prepending managed content changes the final full text, and if a site also runs several policy layers, the rules it sees may be a composite from several parties, where an update by any one of them can invalidate the assertion. One more layer is even easier to omit: HTTP cannot see whether content flows into an index, a summary or a training set after delivery, so declarations and logs cover only the period before delivery and the moment of delivery. These gaps cannot be closed by configuration; they need contracts, platform relationships and after-the-fact reconciliation.

Conclusion: a simple structure is stricter than it looks

If there is no real need to differentiate path rules by crawler, keep a single wildcard group, put the use declaration, the path rules and the sitemap index all inside it, and write the AI crawler roster as a comment. That is stricter than listing a dozen dedicated groups, because no client can slip out of the declaration merely by being named. Where differentiated rules are genuinely needed, accept the cost of copying the declaration into each group and turn group-coverage completeness into an automated assertion. Finally, complete the enforcement layer and the fact layer: edge policy does the blocking, origin logs answer what was actually returned at the time. A twelve-line file plus one reviewable assertion is usually closer to what the site truly wants to say than a 120-line file that merely reads as thorough.

Sources and framing (as of 12 November 2026): group matching, merging groups of the same name, longest path match, Allow precedence at equal length, the 500 KiB read floor, the 24-hour cache, the differing semantics of 4xx and 5xx, and the statement that the rules are not a form of access authorisation all come from the IETF RFC 9309 specification text. The prepended content of Cloudflare managed robots.txt, Bot Preference Sync, the use extension being under test, and the absence of observed impact from syntax warnings come from its developer documentation (page marked updated 2 November 2026) and the official blog, and are official platform statements. A plain-language explanation of a dedicated group replacing the wildcard group also appears in public third-party technical write-ups, consistent with the specification text, and is cited here only as supporting context. The platform managed example and the single wildcard group recommended here are two different trade-offs, set side by side without judging either as right; check the current documentation of your platform before implementing.

Frequently asked questions

If a crawler gets its own dedicated group, does it still follow the rules in the wildcard group?

No. Under RFC 9309 a crawler falls back to the wildcard group only when it matches no dedicated group at all; once it matches a dedicated group, the Allow and Disallow lines and any extension declarations in the wildcard group play no part in its evaluation. Multiple groups with the same name are merged, and only the rules among those named groups are merged.

If Content Signals is written as a comment, can machines still read it?

The comment is a policy text meant for humans; the preference itself is expressed by an extension directive line of the same name. The two should be published as a pair: the comment explains the three purpose terms and the reservation of rights, the directive line carries the concrete values. Parsers handle non-standard directives inconsistently, so no client can be guaranteed to recognise it.

What happens if robots.txt returns a 5xx status?

The specification requires compliant crawlers to assume the entire site is disallowed for the duration, so the impact is far greater than a single mistyped rule; a 4xx such as 404, by contrast, is treated as no restrictions at all. Confirming a 200 status before release takes priority over checking the wording of any one line.
