A signature proves which key signed it: Web Bot Auth does not grant permission

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

Treating “signature verified” as “permission granted” is the most expensive semantic shortcut in agent onboarding. A signature is proof of identity, not a licence: it answers which key signed these requests, not who told the agent to do this, and certainly not who approved the transaction.

Separate identity, authorisation and intent first

The standards-side facts (IETF draft status, checked 10 November 2026): draft-ietf-webbotauth-httpsig-protocol-00 was adopted by the webbotauth working group on 1 September 2026, with authors from Cloudflare and Google; the group was chartered in October 2025 and the draft builds on RFC 9421 HTTP Message Signatures. It is still a working-group draft, not an RFC. An operator publishes a JWKS key directory at /.well-known/http-message-signatures-directory; Signature-Agent is a structured-field dictionary giving one resolvable https URI per signature label; the client signs @authority or @target-uri plus its own Signature-Agent member under the web-bot-auth tag, with created and expires, and the draft recommends a validity of no more than 24 hours.

More important are the three limits the draft sets for itself: a valid signature “says nothing about who operates the Agent, whether the Agent is benign, or whether the request is authorised”; the draft does not require the signature to cover the request body; and it “does not define authorization or delegation”. What verification can put into a log is a key identifier, not “the user consented”. Cloudflare, AWS WAF, Vercel and Akamai have announced verification support; Visa’s Trusted Agent Protocol and Mastercard Agent Pay use the same signatures as an identification base for commerce requests (Mastercard and American Express stated their intent in October 2025), and Google has been testing it for agent requests. That is adoption, not a change to the semantic boundary.

Three places where implementations go wrong

The failures are rarely cryptographic. They come from version compatibility and operational assumptions:

  • The dictionary form of Signature-Agent: earlier drafts sent a bare string; the working-group -00 draft requires a dictionary indexed by signature label, and each signature must cover its own member. Signers may no longer send the bare string, while verifiers may still accept it from older deployments. At least one third-party verifier accepts only the legacy form and rejects -00-compliant signatures outright. Record which draft version you implemented — field rules can still change before an RFC.
  • The directory is an underestimated single point of failure: the draft calls for IANA-registered algorithms, with Ed25519 used in the test vectors and in Cloudflare’s implementation. You must run the directory yourself, highly available, self-signed, cached, with kid rotation. If it goes down, every verification fails — more brittle than keeping a CAPTCHA fallback. The reference library also states publicly that it has not been formally audited. Treat signing as an upgrade layer and keep fail-open behaviour rather than making it the only path.
  • Verification does not replace authorisation checks: card-network agent protocols establish who sent a request and whether it can be replayed; whether a cardholder approved the purchase needs a separate credential layer — AP2 signed mandates, network-side agent tokens, or the merchant’s own risk controls. Skipping limits, category rules and approval flows because a signature is valid mistakes the identity layer for the decision layer.

What to retain for a dispute

Store the verification result, key ID, directory URL, created/expires, draft version, request target and timestamp alongside the order or request log. In a dispute that record can answer which published key signed the requests leading to this order; it cannot answer whether the buyer agreed. Keep the authorisation trail separately, run risk rules as before, and treat the signature result as one input rather than a conclusion. For a content site, passing the verification result into the metering ledger is enough — there is no need to build another identity database.

Summary

Agent identification is moving from guessing User-Agent strings and IP ranges to presenting cryptographic proof, and that is the right direction. Reading that proof as a pass turns the risk from a false block into a false allowance: the former costs traffic, the latter costs money and goods. Earlier we looked at default blocking rules; the thing to remember here is that once the door opens a crack, what walks in is still a stranger who can prove who it is.

Frequently asked questions

Is Web Bot Auth already a formal standard?

Not yet. As of 10 November 2026 it is draft-ietf-webbotauth-httpsig-protocol-00, adopted by the IETF webbotauth working group on 1 September 2026, built on RFC 9421 and chartered in October 2025. It is not an RFC. Field rules may still change, so record which draft version you implemented.

Does a valid signature prove the user authorised the purchase?

No. The draft states explicitly that a signature says nothing about who operates the agent, whether it is benign, or whether the request is authorised; it does not define authorisation or delegation and does not require covering the request body. User intent and spending limits need a separate credential layer such as AP2 mandates, network tokens or the merchant’s own risk controls.

What is most often missed before shipping signature verification?

High availability and kid rotation for the key directory, plus compatibility with the dictionary form of Signature-Agent. Earlier drafts used a bare string; the -00 draft requires a dictionary indexed by signature label, with each signature covering its own member. Some third-party verifiers still accept only the old form and reject compliant signatures. Keep a fail-open fallback such as the existing CAPTCHA path.
