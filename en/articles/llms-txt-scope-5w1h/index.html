How much scope should llms.txt promise: the list, the full text and the trilingual boundary

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

Reading llms.txt as a sitemap for AI is the most popular misreading of this file and the starting point for the whole chain of scope disputes that follows. The proposal text is quite restrained about its own role: a curated list placed at the site root and read on demand at inference time, whose only mandatory part is a single H1 project name. As for llms-full.txt, which many tools expect by default, the proposal does not define it; it is a convention that documentation platforms formed on their own. The 5W1H breakdown of how much scope to promise follows. Conclusion first: the list should be short and accurate, the full-text file should declare its scope before giving content, and trilingual versions should include less rather than mix languages; writing up something not yet done as already done is the most expensive kind of optimism in the machine-readable layer.

What: four files with four non-equivalent scopes

robots.txt is a crawl instruction under IETF RFC 9309, sitemap.xml is a discovery list of URLs meant to be as exhaustive as possible, llms.txt is a curated list of entry points in the sense of the proposal, and llms-full.txt is a tool convention that concatenates body text into one file. The current llmstxt.org text prescribes a fixed order: one H1 project name (the only mandatory section), a blockquote summary, any number of untitled supplementary paragraphs, then one or more H2-separated file lists whose items must contain a Markdown link and may add a note after a colon; a section named Optional has a special meaning, and its links may be skipped when shorter context is needed. The proposal also recommends serving clean Markdown copies of pages, and the second version added two link relations, rel=“alternate” with type=“text/markdown” and rel=“describedby”. Put together, exhaustive listing, curation and inlined body text are three different things, and no one file automatically covers the scope of the other two; naming and promoting llms-full.txt as a whole-site full-text archive has already stepped beyond the proposal boundary.

Why: a vague scope is read downstream as an authorisation or a completeness promise

The value of a curated list is that it filters noise for the reader, but its nature changes as soon as it is read as the site has only this content or this content may be used freely. The proposal states explicitly that llms.txt stops no one, grants no access rights and does not affect whether other paths on the site are crawled; removing a page from the list is not hiding it, and listing a page does not override a robots.txt disallow. Google search guidance (updated 10 July 2026) offers a different framing: a machine-readable file, an AI text file or Markdown is not needed to appear in its search and AI features, keeping llms.txt for other services is harmless, but it neither helps nor harms visibility and ranking in that search. The same file therefore has no ranking benefit on the search side, is treated as an entry map by some agent tools, and is treated as a mere existence check by audit tools — the experimental Agentic Browsing category in Chrome Lighthouse only checks whether the file exists at the root path, validates neither format nor links, and does not prove any AI system has read it. Three readings coexist, and the vaguer the scope, the more likely it is mistaken for a promise.

Who: the proposer, the tool makers and the site each own one segment

The proposal was put forward by Jeremy Howard on 3 September 2024; the current text is a community proposal maintained in a public repository, not an IETF or W3C standard, and no search engine or model provider is obliged to read it. Documentation platforms and toolchains turned derived files such as llms-full.txt and llms-ctx.txt into de facto conventions, with whole-site concatenation promoted jointly by Mintlify and Anthropic being the most frequently cited. What a site operator actually controls is only the copy it publishes: which links, how much detail in the notes, which languages are covered, how often it is updated. The content team is also responsible for translations — on a multilingual site, having a Chinese body text and having a body text in the corresponding language are two different things, and putting untranslated Chinese into an English or German file makes readers of that language read another one and makes language-based automated processing detect the wrong language. The most easily missed link in the division of responsibility is that nobody checks, after the source content changes, whether the list and the full-text file are still consistent.

When: four update moments that do not line up

The proposal text was updated on 10 August 2026 (second version), the search platform guidance on 10 July 2026, the publication moment of the file itself is set by the site, and the downstream reading moment is entirely outside site control. This lack of sync produces two concrete requirements. First, links in the list must point to addresses that exist at the time and return 200; multilingual sites in particular must check whether paths derived from language prefixes really have an artefact, or the list becomes a list of dead links. Second, the file needs a baseline date or a version note: counts such as the number of articles, sections and covered languages change as content is updated, and hard-coding them without a date turns them, months later, into an expired yet deceptively precise promise. By the same logic, if the full-text file includes only some articles, it should state the scope and the selection rule in its header rather than leaving readers to guess from the content that there is probably more that was left out.

Where: the division between a site-level map and page-level markup

llms.txt works at site level and answers which few entry points to read first; schema.org JSON-LD works at page level and answers what this page is, who provides it, whether it has a price and which questions and answers it carries. The proposal text also notes that the file may reference structured data used on the site to help readers understand that information in context, so the two are complementary rather than substitutes. There is a further layer in the directory structure: the file lives at the root path by default, but may sit under a subpath, in which case it covers the URLs below that path, and when several files apply the most specific one should win; the proposal did not adopt /.well-known/, one reason being that on shared hosting many authors control only a single path. A multilingual site usually publishes one list and one full-text file per language prefix, which adds one more dimension to scope: the file for a language lists only pages that actually exist in that language, does not mix in body text from other languages, and does not infer that a path exists in this language merely because it exists in another.

How: write the scope as four verifiable sentences

The first sentence states the nature of the list: this is a curated entry point, not a whole-site URL list, and the complete set of discoverable addresses is defined by the sitemap. The second states the scope of the full-text file: which kind of content is included this time, how many pieces, by what rule items were excluded, and whether matching translations exist; entries without a translation are simply omitted, and the header states that content without a translation into this language is not included, rather than filling the gap with the original. The third states framing and timing: statistics carry a baseline date, prices, article counts and section counts are each marked as site-computed or external data, and vendor self-measurements are kept separate from third-party compilations. The fourth states updating and validation: request every link in the list and confirm 200, run a language-purity check on the visible text of the trilingual files, compare the full-text file with the source body text regularly, and do not Disallow these two files in robots.txt. Four sentences in the file header are less work than explaining the same points repeatedly in the body, and far easier to validate automatically.

Boundaries: what these files cannot prove

The proposal is not a standard and no one is obliged to read it; even if it is read, it constitutes no authorisation, no proof of completeness and no change to search ranking. The framings of the search platform and the toolchains do not agree: one says explicitly that such a file is unnecessary, the other turns it into an existence audit item, and the two describe different systems that cannot be merged into a single conclusion that AI will read it. The full-text file also raises problems the proposal itself does not cover: its size after concatenation, content freshness, and the injection risk of placing whole blocks of untrusted text into a model context are all extra responsibilities of the tool maker and the site. Multilingual versions add one hard boundary — a missing translation is a content fact that file structure cannot conceal, and a language-purity check that does not strip scripts, styles and comments will misread strings in code as body text. What a file can express is the scope the site declares of its own accord; it cannot express whether downstream actually uses it within that scope.

Conclusion: promise less rather than fake completeness

Maintain llms.txt as an annotated recommended-reading list, with few but accurate links, each stating which question the page answers; treat llms-full.txt as a selection explicitly labelled with its scope and baseline date, not as a whole-site archive; keep each of the three languages to its own language, omit missing translations honestly and say so in the header. Add two disciplines: structured data stays at page level, crawl preferences stay in robots.txt, and one Markdown file should not have to carry four jobs. A file published this way will not create false expectations even if no downstream system reads it at all; and once someone really does take data from it, the site can produce records that match.

Sources and framing (as of 12 November 2026): the file format, the only mandatory section, the meaning of the Optional section, Markdown copies, the two link relations added in the second version, and the facts that the file does not block crawling and does not override robots.txt all come from the current llmstxt.org proposal text (a community proposal, page marked second version revised 10 August 2026, original proposal published 3 September 2024). Google statements that no machine-readable file is needed and that llms.txt does not affect its visibility or ranking come from its search guidance (cited by third-party compilations as updated 10 July 2026). The promotion of llms-full.txt by documentation platforms, the fact that the proposal does not define that filename, and the experimental Agentic Browsing category in Chrome Lighthouse performing only an existence check come from third-party technical write-ups and tool documentation, and are tool-maker framing. The descriptions of the proposer, the search platform and the tool makers are set side by side and not merged into a single conclusion; check the current documentation of each party before implementing.

Frequently asked questions

Is llms-full.txt part of the llms.txt specification?

No. The proposal defines llms.txt at the site root and Markdown copies of pages; it does not define the filename llms-full.txt. Concatenating site body text into one file is a convention that documentation platforms formed later. When publishing it, state in the file header that it is a custom artefact and what it includes.

Does listing a page in llms.txt amount to allowing it to be crawled?

No. The list neither authorises nor forbids anything, does not affect robots.txt rules and does not affect indexing; removing a page from the list is likewise not the same as hiding it. Allowing and blocking must be decided separately in crawl rules, edge policy or the authentication layer.

How should articles with no translation be handled on a multilingual site?

Omit them from the file for that language and state in the header that content without a translation into this language is not included. Filling the gap with the Chinese original mixes another language into that language file, which harms readers and makes language-based automated processing judge the language incorrectly.
