The hardest part of open hardware to copy is the gate between generation and flashing

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

The easiest things to copy from a roughly CNY 150 open-source pocket display are the schematic and the enclosure; the hardest is the deterministic check wedged between generating a component in natural language and flashing it onto the device. In 2026, this unglamorous kind of engineering discipline is what separates mature open-hardware projects.

Write 'only show people what needs their attention' as a rule

The project drives a 2.8-inch 480x640 portrait MIPI-DSI display with an ESP32-P4 (dual-core RISC-V up to 400 MHz, 32 MB flash plus 32 MB PSRAM), adds three physical buttons and one four-way joystick with a centre press for 12 configurable gestures, and captures audio on board while doing speech recognition on the desktop. The hardware is unremarkable; the state rules in the repository README are not.

Those rules are deliberately restrained: only active sessions - working, thinking, tool-running and similar - are pushed to the device; a displayed active session keeps receiving updates, so a missed scan does not make it vanish; sessions that reach done or error stay for 60 seconds before disappearing; idle sessions, completed history and internal agent sessions are never pushed; and the number of bubbles is derived from current active sessions, with no user setting. Turning 'do not interrupt the human' into a testable criterion beats building a flashier interface.

Put a gate in front of generation

One level up is the PetUI component runtime: call a Skill inside Codex or Claude, generate a widget in natural language, then let a validation script check the manifest, state machine, button mapping, resource paths and device byte budget item by item. Only a full pass triggers an atomic publish into the component library; the desktop app then syncs it to the device over USB.

The value here is that it admits a fact: generation is uncertain, the device is not. Let a probabilistic system write straight into a small screen with 32 MB of PSRAM and one mistake means reflashing; move the constraints upstream into a script and mistakes happen before release instead. A deterministic gate between generation and device prevents more incidents than another increment of generative capability - and the pattern transfers to any AI-assisted embedded workflow.

Version discipline is the third detail

The repository pins the toolchain to exact versions and separates two chip revisions: the v1 environment uses pioarduino 55.03.32, ESP-IDF 5.5.1, RISC-V toolchain 14.2.0_20250730 and a 360 MHz CPU; v3 uses 55.03.38-1, ESP-IDF 5.5.4, toolchain 14.2.0_20260121, 400 MHz and 24 MHz display timing. Flashing is standardised on esptool 5.4.0, and BUILD.md states outright that v1 and v3 images are not cross-flashable.

Writing 'not cross-flashable' into the documentation instead of relying on a reminder in a chat group is exactly what many hardware projects lack. Open-hardware reproductions usually fail not because the schematic was wrong, but because toolchain, chip revision and firmware versions did not line up.

Bottom line

The three most valuable things in this project are not hardware: testable state rules, a deterministic check after generation, and a toolchain pinned to the revision number. Once AI makes building cheap, reliable reproduction and incident avoidance become the differentiators again. Copying a schematic is quick; copying this discipline takes real work.

Frequently asked questions

What does the PetUI validation script check?

It checks the component manifest, state machine, button mapping, resource paths and device byte budget. Only after everything passes is the component atomically published to the library and synced to the device over USB from the desktop app - keeping the uncertainty of generated output out of the release.

Why keep two separate v1 and v3 build environments?

The two chip revisions use different ESP-IDF, pioarduino and RISC-V toolchain versions, plus different clock and display timings, and the repository states explicitly that images are not cross-flashable. Mixing them produces firmware that will not run - one of the most common causes of failed open-hardware reproductions.

Can this approach transfer to other embedded projects?

Yes. The premise is that generation is probabilistic while a device is deterministic: put scriptable constraint checks between the two, and record toolchain, chip revision and flasher versions in the repository instead of relying on verbal agreements.
