The main site cleared its visual red lines; should the WeChat mini program follow

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

A round of visual consolidation on the site removed gradient backgrounds, rounded cards with a coloured left border, decorative emoji and an overused Latin font stack from the main site style layer; the mini program, meanwhile, still keeps a few gradients, uses the system font stack for body text and carries emoji in some page copy. That produced a task that sounds simple: bring the mini program into line as well. Starting the work reveals that the question is not “whether to change it” but “which layer to align” — copying the main site CSS runs into rpx, platform fonts and navigation-bar rules, while ignoring it entirely makes users feel they are looking at two different products. The 5W1H breakdown follows. Conclusion first: split the red lines into brand judgements and platform adaptations, keep the former consistent across ends, execute the latter according to platform guidelines, and list the exceptions explicitly.

What: four red lines that are not of the same kind

No gradient backgrounds, no emoji as decoration, no rounded cards with a coloured left border, no overused font stack read like a single checklist but actually belong to two different kinds. The first three are brand judgements: they set the tone — restraint, not piling up information with ornament, not filling the screen with meaningless figures and icons. The fourth is entangled with platform convention: what the main site bans are explicit stacks such as Inter, Roboto, Arial, Fraunces and system-ui that have been used over and over, whereas the mini program uses the system sans-serif font by default, a mechanism the platform provides to keep text legible across device models, not designers lazily picking a ubiquitous font. Sweeping all four as the same kind of violation leads to the conclusion that the mini program must import a custom font package, which adds size while introducing loading and licensing problems. The right approach is to classify first: which things are never done on any end, and which the platform has already decided for you and need only not be layered on top of.

Why: the cost of cross-end consistency lands on maintenance, not the first version

Aligning the first version is always easy; the difficulty comes six months later. If the red lines are frozen as the two stylesheets matching line by line, every platform update and every main site redesign forces a human to decide which differences are legitimate exceptions and which are missed changes; exceptions pile up until nobody dares touch the list. In the opposite direction, if all that is written is roughly the same style, the mini program slowly grows its own decorative habits in practice, and a user arriving from the main site sees a different visual language. What really has to be controlled is consistency of judgement, not equality of property values: whether a gradient should be used, whether emoji may enter body copy, whether a card needs a coloured border — these answers must be the same on both ends; how many rpx to use, how type sizes are graded, who owns the font may differ. The rpx mechanism in the WeChat open documentation illustrates the second category precisely: page width is fixed at 750rpx and the platform converts it into real dimensions on different device models, so adaptation rules of this kind should not be overwritten by the main site CSS pixel values.

Who: brand judgement, platform rules and end implementation each belong to someone

Brand and visual judgement are set by the site itself and hold across ends; platform rules are set by platforms such as WeChat, whose official design guidelines and size-unit documentation state which interaction conventions are uniform and which can be customised — third-party compilations often mention constraints such as the top-right official menu not being customisable, but details of this kind should follow the current official documentation rather than anecdotal posts taken as evidence; end implementers land the work within those constraints and register whatever cannot or should not be done as exceptions. One more role is easily overlooked: review and release. The main site takes effect on push, while the mini program goes through its own platform release process, so the two ends naturally cannot update at the same time. Cross-end consistency therefore cannot demand identical at the same instant, only the same judgement with traceable exceptions. With responsibilities separated, a difference prompts the question “registered exception or missed change?” rather than “whose stylesheet is newer”.

When: convergence happens when the main site is final, review happens before each end releases

The best moment is after the main site visual design is final and before the next mini program release: write down the judgements the main site finally adopted first, then scan each end, so as not to keep aligning against a version that is still changing. The real order in the project was the same — the main site first converged its last two gradients, returned the font stack and completed a full-page screenshot review, and only then were the mini program leftovers put on the to-do list; had both ends changed at once, the main site would likely have finished and then rolled back, with the mini program wasting a round of changes following it. After that, every main site visual change triggers one cross-end check, and every mini program release re-checks whether the exception list still holds. Because the two release rhythms differ, alignment is a continuing state rather than a one-off task: the record needs a check date and the version of each end, not just a note saying “unified”. Caches and older client versions also let users see different versions for a while; that belongs to the release mechanism and does not count as visual inconsistency.

Where: the checklist lives in one place, the exceptions live inside each end

Maintain one cross-end red-line checklist with two columns. The first column is prohibitions, effective on both ends, written as judgements rather than CSS values — no gradient backgrounds, no decorative emoji, no rounded cards with a coloured left border, no importing overused explicit font stacks, no piling up meaningless figures and icons. The second column is platform exceptions, written per end: the mini program using rpx and the platform default font stack is an adaptation mechanism, so no custom font is layered on; navigation and capsule areas follow platform rules; sizes, type grades and line heights follow platform legibility. Keep the checklist in the project conventions and reflect the exceptions in end-side code comments and check scripts, so a scanner can tell violating a prohibition from hitting a registered exception. The rendered page should agree too: information blocks use solid colours instead of coloured-border cards, so both ends look like the same language even though the implementation values differ. Keeping the checklist and the exceptions apart is what makes exceptions traceable rather than a quietly loosened opening.

How: turn cross-end alignment into four actions

First, freeze the judgements: once the main site is final, write the prohibitions as short sentences with no property values, so “0 gradients” does not turn into a demand that a particular selector in a particular file be a solid colour. Second, scan each end: check styles and copy against the prohibitions, record hit positions and counts, but do not count platform defaults as violations; a hit on the system font stack, for example, belongs in exceptions rather than in pending fixes. Third, register exceptions: each one states the platform, the reason, the basis (official documentation or an engineering trade-off) and a review date, and no exception without a basis is registered. Fourth, wire it into pre-release checks: each end runs the prohibition scan on its own, outputs two numbers — violations and registered exceptions — and files both in the release record. Then the day the mini program adds a gradient, the tool reports a violation; the day the platform changes its font mechanism, a person updates the exception note instead of throwing the whole checklist out. None of the four actions needs a stylesheet shared by both ends.

Boundaries: the parts that cannot and need not be unified

Platform-level interaction conventions should not be overridden by main site habits: navigation bars, capsule areas and back behaviour follow the current platform rules, and third-party descriptions of such constraints are only leads, with the official documentation as the final word. Size systems cannot be unified either: the main site works in CSS pixels and media queries, the mini program in rpx converted by the platform, and forcing one side values onto the other only creates new layout breakage. Font licensing and package size are another hard constraint — importing a custom font package for the sake of complete visual identity can bring loading, copyright and performance costs with no guaranteed visible gain. There is also the time gap caused by release: the mini program goes through a platform release flow and users may stay on an older version, so differences during that window belong in the record and are not missed changes. Finally, this note is about consistency of visual and copy judgements; it does not cover whether the two ends align on feature scope, data framing or commercial framing, which is a separate question.

Conclusion: unify the judgement, allow exceptions, and write the exceptions down

The easiest way for cross-end consistency to go wrong is to treat looking the same as the goal. The steadier goal is this: the same brand judgement gets the same answer on both ends, and every difference has a reason and a date in the exception list. Write prohibitions as short sentences without property values, register platform adaptation mechanisms as exceptions with a basis, and have each end scan before release and report both the violation count and the exception count. Then, when the mini program clears leftover gradients and removes decorative emoji from copy, it is not also asked to replace the platform font stack; and if the main site ever wants to bring gradients back, it hits this cross-end checklist first and forces the team to decide again. What has to align is the decision, not the stylesheet — the rework that sentence saves is usually far more than one thorough stylesheet rewrite.

Brand judgements and platform adaptations are written side by side, with no averaging between them.

Frequently asked questions

Does the mini program using the system font stack count as violating the ban on overused fonts?

Under the classification used here, no. What the main site bans are explicitly declared font stacks that have been used repeatedly; the platform default sans-serif font in the mini program is an adaptation mechanism. It should be registered as a documented exception rather than offset by importing a custom font package, which would add size, loading and licensing costs.

Could both ends share one stylesheet to rule out inconsistency entirely?

Not recommended. The main site works in CSS pixels and media queries, the mini program in rpx converted by the platform, and each has its own platform-level interaction conventions. A shared stylesheet would turn adaptation differences into a long series of hard-coded special cases. What should be unified is the set of prohibitions; concrete values may differ but need a recorded reason.

The main site is finalised; should the mini program be changed immediately?

It is better to wait until the main site judgement is frozen, then review the exception list before the next mini program release. The two ends publish through different mechanisms and cannot take effect at the same moment by nature; the record should carry a check date and both versions, and treat the time gap as a known fact rather than a missed change.
