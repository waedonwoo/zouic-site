Aggregation is not reposting: which layer should carry the index card’s content boundary

Compute industry notes · GeekWaedon @GeekWaedon

GeekWaedon @GeekWaedon · November 2026

The first screen of ZouIC carries one sentence: it aggregates open-source hardware projects from GitHub, Hackster.io, CrowdSupply, Hackaday, Seeed Studio and similar platforms, with unified filtering and pagination; all projects are for developers’ reference only, copyright and licensing remain with the original authors, and each project follows its own open-source licence. The sentence is perfectly clear, but it is a page note addressed to people. The decision an aggregation site really has to make is not about wording but about layers: what the data layer actually stores, what the structured-data layer declares as the main entity, and which links the machine-readable layer publishes as its own content. As soon as one layer crosses the line, the sentence on the first screen becomes a one-sided wish. The 5W1H breakdown follows. Conclusion first: an index card is a description about a project, not a copy of the project; that boundary has to be written once in each of the four layers, and the four statements have to corroborate one another.

What: two kinds of “content” that keep getting conflated

An aggregation site actually produces two things. The first is the index card: project name, a one-line description, source platform, original link, filter tags, inclusion date, plus the site’s own categorisation and commentary — descriptive content the site authored itself. The second is the source project itself: schematics, firmware, the bill of materials (BOM), README, tutorial body text and product specifications in the repository, whose copyright and licensing stay with the original authors. The confusion rarely starts with plagiarism; it starts with a cache made “for easier searching”. Someone pulls the full README into their own table so site search can hit it; then stores a few schematics as local images so external links cannot break; then, to make the detail page look complete, splices in the tutorial body text too. Each step looks reasonable on its own, but four steps later the line “for developers’ reference only” no longer describes what is actually happening. The test can be kept very plain: after deleting the local copies, can the site rebuild the card from the original link alone? If yes, it is still indexing; if no, it is already reposting.

Why: search engines, machine readers and original authors do not want the same sentence

The getting-started guidance from Google Search Central puts it bluntly: write your own content, grounded in your own understanding, rather than copying or merely restating what others have already published; it also notes that having duplicate content on a site does not itself violate the spam policies, yet the same information spread across a pile of different URLs creates a poor experience and wastes crawl resources. The canonicalisation documentation adds two easy-to-miss details: rel=canonical is a hint, not a rule, and the platform may still pick a different canonical URL; and do not use robots.txt for canonicalisation, because a URL blocked from crawling can still be indexed, just without its content being fetched. The three parties’ demands therefore diverge. A search engine wants to know whether the card has independent value and which address counts as the primary one; a machine reader wants to know which real project the description maps to and what the licence is; the original author wants attribution, the original link and an unaltered licence. One line saying “copyright remains with the original authors” cannot answer all three at once, because they read three different layers — the visible page copy, the structured data and the link relations — not the same one.

Who: four parties each own a segment, and nobody automatically owns consistency

The source platform decides what the project page contains, where the licence is attached and when the page is taken down; the original author decides the scope of the licence and may release different artefacts under different licences on different platforms; the site operator decides which fields to collect, how much of their own description to write and which links go into the machine-readable list; and search engines and AI clients decide how to interpret those markers. The schema.org vocabulary definitions lay out exactly these four parties’ boundaries: sameAs points to a reference page that unambiguously indicates the item’s identity; isBasedOn says which resource this work derives from or adapts (and has superseded isBasedOnUrl); license points to the licence document governing this content; citation is a reference to another work; and mainEntityOfPage states what a given page is primarily about. These fields are not decoration. Putting a source repository’s link into sameAs asserts “this card and that repository are the same identity”; putting it into isBasedOn asserts “this card is a derivative work of that project”. The two assertions carry entirely different responsibilities, and the cost of filling one in wrongly falls on the site, not on the template that filled the field.

When: four moments that do not stay in sync

First is the moment of inclusion: the site fetches metadata and writes an inclusion date, the only timestamp that can prove what was seen at the time. Second is the moment of source change: the repository changes licence, is archived, is deleted, a product page is taken down, a tutorial is edited — and the site may never be notified. Third is the site’s export moment: a static export freezes the current card into HTML, after which the page no longer follows the source until the next re-export. Fourth is the external reading moment: a search engine or machine client may be holding a version cached weeks earlier. Collapsing those four moments into one “current state” is the most common source of distortion on an aggregation site. The engineering answer is not real-time sync — that introduces more crawling and compliance problems — but making time explicit: the card carries an inclusion date and a last-checked date, the machine-readable list carries a baseline date, breakage and licence changes get their own status, and “last checked” must not be read as “content verified correct” but only as “the link and fields were accessed on this day”. Google’s canonicalisation documentation adds one more reminder: different language versions count as duplicate pages only when the main content is still in the same language, so trilingual index cards must not point a single canonical back and forth among themselves; each has to self-reference and close the loop with hreflang.

Where: four layers of placement; miss one and the site is read as something else

The data layer should hold only metadata, the original link, source platform, licence pointer, inclusion and check dates, and the site’s own description and tags; body text, schematics, firmware and product images stay on the source site and are referenced by link. The page layer writes “copyright and licensing remain with the original authors, each under its own open-source licence” as visible copy, and makes the original link a prominent clickable exit rather than hiding it in the footer. The structured-data layer uses sameAs for the authoritative identity page, isBasedOn or citation for derivation and reference, license for the licence address, and points the mainEntityOfPage of the entity at this card on the site, making explicit that the site describes an item about the project rather than the project itself. The machine-readable layer (sitemap, lists such as llms.txt) lists only the site’s own page addresses and does not slip source project pages into the site list to pass them off as its own content. The four layers must agree: if any one of them surfaces source full text or lists a source page in the site’s list, the other three statements are automatically void. When the site runs dead-link and sitemap checks, it should also distinguish “does a site-owned address exist” from “is an external link still alive” — those are not one and the same check.

How: turn the boundary into four reviewable assertions

Assertion one, on the data layer: the local tables contain no body-text field, no design-file binary and no image copy from a source project; if thumbnails genuinely exist, their purpose and source are labelled separately and they can be cleared with one action. Assertion two, on the link layer: every index card’s source link resolves, points at the original site rather than a site-owned mirror, and its licence address (if any) matches what the card states; when the original link breaks, the card enters a pending-review state rather than being silently deleted or treated as normal. Assertion three, on the markup layer: sameAs and isBasedOn do not point at the same URL to say the same thing, license is not conflated with the source platform’s homepage, and the trilingual cards each self-reference a canonical and form a closed hreflang loop. Assertion four, on the list layer: every address in the sitemap and machine-readable lists belongs to the site’s own domain, and source project pages appear only as links inside cards. All four assertions go into the pre-release self-check, not into an editorial guideline people are expected to follow voluntarily. Only after that step does a discussion about whether to snapshot sources or add summaries have a shared baseline.

Boundaries: where this decomposition stops holding

It answers whether the site itself has crossed a line, not whether the source is clearly licensed. One repository may put code, schematics and documentation under different licences, or may have no licence file at all; in that case writing “each under its own open-source licence” is only relaying a statement and cannot complete the authorisation on the original author’s behalf. The schema.org fields are vocabulary definitions and do not guarantee that any search engine will read them or reassign ownership on that basis; rel=canonical is, per the platform documentation, only a hint, and the site cannot use it to force an identity. Static export adds another lag: the page is a snapshot of one moment, and a machine reader may hold an even older cache, so either can differ from today’s source site. The more practical gap is that the HTTP layer cannot see whether content, once fetched, is used for indexing, summarisation or training; declarations and logs cover only the moment of delivery. None of these gaps can be closed by adding one field. They can only be handled by labelling a baseline date, keeping check records, and deferring to the original author’s page when a dispute arises.

Conclusion: write “not reposting” into the structure, not into a statement

A copyright notice on the first screen has value, but it is a statement; the real boundary is the fact jointly constituted by the data structure, link relations, markup fields and list scope. The recommendation is to invert the order: first decide what is not stored locally, then what goes into the card, then fill in sameAs, isBasedOn, license and the self-referencing canonical, and finally turn four-layer consistency into an automated assertion at release time. That way, even if full-text summaries or offline snapshots are added later, they immediately collide with one of the assertions and force the team to decide again, rather than quietly turning the aggregation site into a reposting site while nobody notices. It is also easier for the reader: on one card they can see what this is, where the original site is, who set the licence and when the site last checked, and then decide for themselves whether to click through.

The meanings of sameAs, isBasedOn (which supersedes isBasedOnUrl), license, citation and mainEntityOfPage come from the schema.org CreativeWork and SoftwareSourceCode vocabulary definitions and are normative specification text. The points that duplicate content does not itself violate the spam policies, that content has to be written by oneself, that rel=canonical is a hint rather than a rule, that robots.txt must not be used for canonicalisation, and that different language versions count as duplicates only when the main content is still in the same language come from the Google Search Central getting-started guide and canonicalisation documentation and are official platform statements. Third-party SEO compilations discussing a “duplicate-content penalty” point in the same direction as this conclusion and are used only as supporting context, not as evidence. A normative vocabulary definition is not the same as a search engine’s actual adoption behaviour; the two are set side by side and no average is taken between them.

Frequently asked questions

If a card stores the full README of a source project, is it still aggregation?

By the test used here, it is no longer pure indexing. The reviewable criterion is whether the card can be rebuilt from the original link alone after the local copy is deleted. If it cannot, treat it as reposting: state the authorisation and attribution explicitly instead of continuing to describe it as “for developers’ reference only”.

What goes wrong if both sameAs and isBasedOn point at the source link?

The two fields assert different relations: sameAs states identity, isBasedOn states that this work derives from that resource. If one card uses both fields to point at the same URL for the same purpose, a machine reader cannot tell whether the site is saying “this is that project” or “this is a work based on that project”. Pick the one you need and use citation or an ordinary link for the rest.

Does adding source project pages to the sitemap get them indexed faster?

It should not be done. A sitemap expresses the set of addresses the site itself wants crawled; listing someone else’s pages changes no ownership and distorts what the list claims. Source pages belong in the card as clickable links, and the site’s own list carries only the site’s own addresses — the easiest of the four layer-consistency checks to verify.
