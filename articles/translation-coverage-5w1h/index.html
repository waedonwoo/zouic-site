译文没跟上时，页面该显示什么

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

多语站点上线一段时间后，英德页面偶尔会冒出一两句中文。这类问题几乎都不是翻译遗漏本身造成的，而是模板里那句看起来很稳妥的兜底：取不到译文键，就用写在模板里的中文默认值。系统没有报错，页面也返回 200，只是读者在英文页里读到了另一种语言。下面按 5W1H 把「译文没跟上时该显示什么」拆开。结论先说：缺译必须由内容清单明确决定，不能由渲染层的默认值隐式决定；宁可少收一条内容，也不要把语种混排当成兼容策略。

何事 · What：三处会让中文漏出去的地方

第一处是界面字典：模板普遍用「按键取值、取不到就回退到写在模板里的中文」这种写法，新增功能时若只补了中文模板而忘了同步英德字典，默认值就会直接出现在页面上，包括 aria-label、placeholder、图片 alt 这类不会被人眼一眼看到、却会被屏幕阅读器读出来的文本。第二处是正文译文：多语站点常按「基础语言 → 英文 → 德文」的方式叠加字典，只要某一层少了键，就会回落到更靠前的语言；长文如果按块对齐，缺一块还会让后续块整体错位。第三处是全文归档类文件：拼接到英文或德文版本里时，若无对应译文却照样把原文塞进去，整个文件的语种纯度就被破坏。三处的共同点是：兜底逻辑都在提升「不空白」，却把「用哪种语言」这个决定从内容侧悄悄挪到了渲染侧。

何因 · Why：语种纯度是承诺，不是美观问题

读者进入某个语言版本，默认这一页的内容都属于该语种；搜索与自动处理同样会把页面语言当成判断依据。混排带来的代价有三层：对读者是不连贯，对语言检测是误判，对下游是「这一页到底算哪个版本」变得模糊。更麻烦的是它会伪装成正常状态：页面渲染成功、状态码 200、字数也够，只有做语种纯度检查才会暴露。检查本身也有陷阱——若直接对整份 HTML 统计中文字符，脚本块与样式块里的中文注释、模板作者卡片里的中文、以及注释掉的旧文案都会造成误报；反过来，MarkupSafe 把英文撇号与直引号转义成实体，也可能被粗糙的规则误当作异常。于是「英德页中文残留为零」这个指标，必须先定义清楚统计的是哪一部分文本：通常是剔除 script、style 与 HTML 注释之后的可见正文，外加 title、desc、aria-label 这类元数据。

何人 · Who：内容、译文、模板与校验各负其责

内容团队决定哪些条目在某个语种确实存在，并对「略过」还是「保留占位说明」负责；译文模块负责逐块对齐，包括标题、摘要、关键词、常见问题与正文每一块；模板负责不把中文默认值当兜底输出给非中文页面；校验脚本负责在发布前把覆盖情况算成一张表，而不是只报一个总数。责任划分里最容易缺的是最后一方：没有自动校验时，覆盖缺口往往由读者先发现。还有一个常被调用方忽略的角色——屏幕阅读器用户：按钮的 aria-label、搜索框的 placeholder、二维码图片的 alt 都在可见性检查的边界上，人眼扫一遍页面看不出来，却实实在在属于「页面显示了什么」。把这些文本纳入字典覆盖检查，和把正文译完同等重要。

何时 · When：三种不同步的更新时刻

源文更新、译文更新、字典更新并不同步：一篇中文文章改了导语，英德译文未必当天跟进；一个新 UI 组件上线，界面字典可能几个语种一起补，也可能先上中文。因此覆盖检查不能只在「大版本发布」时做，而应挂在每次内容或模板变更之后。多语叠加的顺序也有时间含义：基础语言是默认层，英文与德文是覆盖层，一次新增键若只进了中文模板，另外两层在补齐之前都处于「会露中文」的窗口期。合理的做法是让这个窗口在发布流程里可见——把「缺失键清单」作为导出前的门槛，清单非空就不允许发布对应语种；而不是靠上线后巡检去捞。至于译文质量复核，节奏可以慢一些，但覆盖与块数对齐必须在每次导出时实时验。

何地 · Where：四类落点要分开验

第一类是页面可见正文与标题，检查对应语种的文本是否存在、块数是否与源文一致。第二类是元数据：title、description、keywords、H1、结构化数据里的名称与联系信息，这些内容常从另一套字典取值，正文译完不代表它们也译完。第三类是可访问性文本与界面控件：aria-label、placeholder、alt、按钮文案，属于最容易漏译的一组。第四类是归档型文件：清单、全文文件与 sitemap 的语言版本，规则应当更严——没有本语种译文的条目直接略过，并在文件头说明筛选规则，而不是保留原文占位。四类的共同真源是「哪些键 / 哪些条目在本语种确实有译文」的清单，检查脚本应当基于清单比对，而不是基于页面上碰巧有没有出现中文字符。

如何 · How：把覆盖做成四条可执行的规则

第一条：扫描所有模板里的取值表达式，凡回退值是中文的键，都必须同时存在于英德字典；把「缺失键数量为零」设为导出门槛。第二条：正文按块对齐，逐篇核对源文与两个语种的块数、常见问题条数、标题与摘要字段，任何一项不等就阻断发布，因为块数错位会让后文整体串位。第三条：统计可见文本的语种纯度时，先剔除 script、style 与 HTML 注释，再检查 title、desc、aria-label 等元数据；把既有的实体转义与模板作者卡片列入白名单，避免误报掩盖真实问题。第四条：归档文件按「有译文才收录」生成，文件头写明范围与基准日。四条规则产出的结果是一张覆盖表——每种语言多少篇正文、多少界面键、多少归档条目，以及缺口在哪，而不是一个笼统的「已支持三语」。

边界：覆盖检查证明不了译文质量

块数对齐、键齐全、无中文残留，只能说明结构完整与语种纯净，不能说明译得准确、术语一致或语气得体；机翻、逐字硬译、专业名词前后不一，都能轻松通过这四条规则。反过来，某些合理的例外也会被严格规则拦下：品牌名、产品官方中文名、法规条文原名、代码标识符、引用他文时的原文片段，都可能在一个语种页面里正当出现非该语种的字符，需要白名单而不是一刀切。还有一层技术边界：转义实体、排印引号与直引号的差异会让基于字符的扫描产生噪声，检查口径必须固定下来并写进脚本，否则每次结果都不可比。最后，覆盖与语言信号是两套系统：hreflang 全绿只说明版本关系成立，不说明某个版本里的文本真的属于该语种。

结论：让缺译成为一个显式决定

把「哪些内容在本语种存在」做成一份清单，模板与导出脚本只消费清单；缺键不再回退中文，而是让发布前的断言失败；归档文件宁可少收，也要在文件头写明范围。再把可见文本、元数据与可访问性文本一起纳入语种纯度检查，并把合理的非本语种例外列成白名单。这样「支持三语」才是一句可以核对的话：每个语种覆盖多少条、块数是否对齐、页面上有没有混排，都能当场算出来。译文质量仍需人工复核，但至少不会出现「读者比我们先发现露中文」这种本可避免的失误。

数据与口径（基准日 2026-11-12）：本文所述「基础语言 → 英文 → 德文」字典叠加、缺键回退中文默认值、按块逐篇对齐、剔除 script 与 style 后再统计中文字符、HTML 实体转义属既有现象而非译文问题、排印引号可避免转义误报，均为站点自身的多语发布工程口径与公开技术整理，非任何平台规范。hreflang 的双向与自引用要求出自 Google Search Central 文档，本文只引用其关系语义，不把覆盖检查与语言信号混为一谈。第三方机翻质量、各平台语言检测行为未作独立核验，不作为结论依据；实施前请以自家模板、字典与导出脚本的实际行为为准。

常见问题

模板里写中文默认值做兜底，有什么问题？

问题在于把语种决定交给了渲染层。英德字典缺键时，页面会直接显示中文，而且状态码、字数都正常，只有语种纯度检查能发现。建议让缺键在导出前的断言里失败，而不是静默回退。

检查英德页面有没有中文，直接搜中文字符可以吗？

不够准。脚本与样式块里的中文注释、HTML 注释、模板作者卡片都会误报；应剔除这些部分后再统计可见文本，同时单独检查 title、desc、aria-label 等元数据，并给品牌名等正当例外留白名单。

没有译文的文章，能不能先放原文占位？

在归档型文件里不建议。原文占位会破坏该文件的语种纯度，也会让基于语言的自动处理判断错误；更稳妥的是直接略过，并在文件头写明「不收录无本语种译文的内容」与范围基准日。
