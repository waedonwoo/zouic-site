主站清零的视觉红线，小程序要不要跟

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

站点做过一轮视觉收敛：主站样式层里不再有渐变背景、不再用带左侧彩色边框的圆角卡、不再用 emoji 当装饰，字体栈也换掉了被用滥的西文字体；而小程序那边还留着几处渐变、正文用系统字体栈、若干页面文案里带 emoji。于是有了一个看似简单的任务：把小程序也对齐。真动手才发现，问题不是「改不改」，而是「对齐到哪一层」——照搬主站 CSS 会撞上 rpx、平台字体与导航栏规范；完全不管又会让用户觉得是两个产品。下面按 5W1H 拆开。结论先说：把红线拆成品牌判断与平台适配两类，前者跨端一致，后者按平台规范执行，并显式列出例外。

何事 · What：四条红线，性质并不相同

「不用渐变背景」「不用 emoji 当装饰」「不用带左侧彩边的圆角卡」「不用被用滥的字体栈」看似是一份清单，实际分属两种性质。前三条是品牌判断：它们决定的是气质——克制、不靠装饰堆信息、不把无意义的数据和图标铺满屏。第四条则与平台惯例纠缠：主站禁的是 Inter、Roboto、Arial、Fraunces、system-ui 这类被反复使用的显式字体栈，而小程序默认使用系统无衬线字体，是平台为保证跨机型可读性提供的机制，不是 designers 偷懒选了烂大街字体。把四条当成同一种「违规」去扫，会得出「小程序必须引入自定义字体包」这种既增加体积、又引入加载与授权问题的结论。正确做法是先分类：哪些是不管在什么端都不做的，哪些是平台已经替你决定、只需不额外叠加的。

何因 · Why：跨端一致的成本落在维护，不在首版

首版对齐总是容易的，难的是半年后。如果小红线写死成「两端样式表逐条相同」，每次平台更新、每次主站改版，都要人工判断哪些差异是合理例外、哪些是漏改，例外越积越多，最后没人敢动清单。反过来，如果只写一句「风格差不多就行」，小程序就会在实践中慢慢长出自己的装饰习惯，用户从主站点进小程序会看到另一套视觉语言。真正要控制的是判断的一致性，而不是属性值的相同：渐变该不该用、emoji 能不能进正文、卡片要不要彩边——这些答案两端必须一样；具体用多少 rpx、字号怎么分级、字体交给谁，这些可以不同。微信开放文档给出的 rpx 机制正好说明后一类：页面宽度统一为 750rpx，由平台换算成不同机型上的实际尺寸，这类适配规则不应被主站的 CSS 像素值覆盖。

何人 · Who：品牌判断、平台规范、端实现各归谁

品牌与视觉判断由站点自己定，跨端有效；平台规范由微信等平台定，官方设计指南与尺寸单位文档说明哪些是统一的交互约定、哪些可以自定义——第三方整理里常提到右上角官方菜单不可自定义一类约束，这类细节应以官方当期文档为准，不凭经验贴当作依据；端实现者负责在约束内落地，并把「做不到或不该做」的部分登记成例外。还有一类角色容易被忽略：审核与发布机制。主站推送即可生效，小程序要经过平台自己的发布流程，两端天然不可能同时更新。因此跨端一致性不能要求「同一时刻相同」，只能要求「同一判断、例外可查」。把责任分清后，出现差异时问的是「这是登记的例外还是漏改」，而不是「谁的样式表更新」。

何时 · When：收敛发生在主站定稿时，复核发生在两端发布前

最合适的时机是主站视觉定稿之后、小程序下一次发版之前：先把主站最终采用的判断写下来，再逐端扫描，避免对着一个还在改的版本反复对齐。项目里的实际顺序也是这样——主站先把最后两处渐变收敛、字体栈回归、整页截图复核完毕，才把小程序残留列为待办；如果当时两端同时改，很可能出现主站改完又回滚、小程序跟着白改一轮。之后每次主站视觉变更，触发一次跨端检查；每次小程序发版前，复核例外清单是否仍成立。两端发布节奏不同，所以「对齐」是一个持续状态而非一次性任务：记录里要有检查日期与两端各自的版本，而不能只写「已统一」。缓存与旧版本客户端也让用户在一段时间内看到不同版本，这属于发布机制，不算视觉不一致。

何地 · Where：清单落在一处，例外落在端内

建议维护一份跨端红线清单，分两栏：第一栏是禁止项，两端都生效，写清判断而不写 CSS 值——不铺渐变背景、不用装饰性 emoji、不用带左侧彩边的圆角卡、不引入被用滥的显式字体栈、不堆砌无意义的数据与图标。第二栏是平台例外，逐端写：小程序采用 rpx 与平台默认字体栈属于适配机制，不额外叠加自定义字体；导航与胶囊区域按平台规范执行；尺寸、字级、行高以平台可读性为准。清单放在项目约定里，例外则在端内代码注释与检查脚本中体现，这样扫描工具能区分「违反禁止项」和「命中已登记例外」。页面呈现上也要一致：信息块用纯色、不用彩边卡片，两端看起来是同一套语言，但实现值可以不同。把清单和例外分开放，是为了让例外有据可查，而不是变成悄悄放宽的口子。

如何 · How：把跨端对齐做成四个动作

第一，冻结判断：主站定稿后把禁止项写成不含属性值的短句，避免把「0 渐变」误写成「某文件某选择器必须是纯色」。第二，逐端扫描：按禁止项检查样式与文案，记录命中位置与数量，但不把平台默认值算进违规；例如系统字体栈命中应归入例外而非待改。第三，登记例外：每条例外写平台、原因、依据来源（官方文档或工程取舍）、复核日期，没有依据的例外不登记。第四，接入发布前检查：两端各自跑一遍禁止项扫描，输出「违规数」与「已登记例外数」两个数字，发布记录里同时留档。这样哪天小程序新增了一处渐变，工具会报违规；哪天平台改了字体机制，人可以更新例外说明，而不是把整份清单推倒重来。四个动作都不需要两端共用一份样式表。

边界：统一不了、也不必统一的部分

平台级交互约定不该被主站习惯覆盖，导航栏、胶囊区域、返回行为等按平台当期规范执行；第三方整理对这类约束的描述只能作线索，最终以官方文档为准。尺寸体系也无法统一：主站按 CSS 像素与媒体查询，小程序按 rpx 由平台换算，把一边的数值硬套到另一边只会制造新的破版。字体授权与包体积是另一条硬约束，为追求视觉「完全一致」引入自定义字体包，可能带来加载、版权与性能代价，收益却未必可见。还有发布机制造成的时差：小程序需经平台发布流程，用户端还可能停留在旧版本，这段时间的差异应写进记录而不是算作漏改。最后，本文讨论的是视觉与文案判断的一致性，不涉及两端功能范围、数据口径与商业口径是否同步，那是另一个问题。

结论：统一判断，允许例外，例外要写明

跨端一致性最容易走偏的地方，是把「看起来一样」当成目标。更稳的目标是：同一个品牌判断在两端得到同一个答案，差异都能在例外清单里找到理由与日期。建议把禁止项写成不含属性值的短句，把平台适配机制登记成有依据的例外，两端发布前各自扫描并同时报「违规数」与「例外数」。这样小程序清理残留渐变、去掉文案里的装饰性 emoji 时，不会被顺带要求换掉平台字体栈；而主站哪天想重新引入渐变，也会先撞上这份跨端清单，迫使团队重新拍板。要对齐的是决定，不是样式表——这句话省下的返工，通常比一次彻底重写样式多得多。

数据与口径（基准日 2026-11-13）：主站视觉收敛结果（样式层 0 渐变、无 Inter / Roboto / Arial / Fraunces / system-ui 显式字体栈、首页与服务页无 emoji、不用带左侧彩边的圆角卡、不堆砌无意义数据与图标），以及小程序残留（若干处渐变、正文系统字体栈、若干页面文案含 emoji）出自 ZouIC 项目设计约定与源码现状，属站点自身口径。rpx 以 750rpx 为页面宽度基准、由平台按机型换算实际尺寸，出自微信开放文档与微信开放社区的官方教程，属平台官方口径；官方设计指南地址为 developers.weixin.qq.com/miniprogram/design/。第三方关于导航栏不可自定义、组件库与设计规范的经验整理只作方向性线索，不写进结论，具体约束以平台当期官方文档为准。品牌判断与平台适配并列写出，不取平均。

常见问题

小程序用系统字体栈，算不算违反「不用烂大街字体」？

按本文的分类不算。主站禁的是被反复使用的显式字体栈，小程序使用平台默认无衬线字体是适配机制。它应登记为有依据的例外，而不是为了对齐去引入自定义字体包，后者会带来体积、加载与授权代价。

能不能让两端共用同一份样式表，彻底避免不一致？

不建议。主站按 CSS 像素与媒体查询，小程序按 rpx 由平台换算，还有各自的平台级交互约定。共用样式表会把适配差异变成一连串硬编码特例。要统一的是禁止项判断，具体值允许不同但需登记理由。

主站已经定稿，小程序还要不要马上改？

建议等主站判断冻结后再做，并在小程序下一次发版前复核例外清单。两端发布机制不同，天然不会同时生效；记录里应写检查日期与两端版本，把时差作为已知事实，而不是当作漏改。
