长上下文的成本大头不是算力，是「把历史记住」

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

同样一张 GPU，换一套 KV Cache 管理方式，能服务的请求量可以差好几倍。2026 年推理系统最实在的性能红利，不来自新芯片，来自把「记历史」这件事从 GPU 显存里搬出去。

先把两个阶段的矛盾说清

大模型推理分 prefill（把整个 prompt 算一遍，算力密集）与 decode（逐 token 生成，内存带宽密集）。传统部署把两者塞在同一张卡上，结果很别扭：长 prompt 的 prefill 会把正在生成的请求卡住，TTFT 与 TPOT 互相拖累；同时每个会话的 KV Cache 都占着宝贵的 HBM，上下文越长、并发越高，显存越先见底。

PD 分离把两类请求分到不同节点，再用一个共享的分布式 KV Cache 池把中间状态传过去。听起来只是调度调整，实际把「显存容量」从单卡约束变成了集群级资源池问题——HBM、主机 DRAM、SSD、CXL 内存池构成一个层级，热数据留近处，冷数据下沉。

一个开源项目把这条路走通了

Mooncake（月之暗面 Kimi 与清华 MADSys 牵头，FAST '25 最佳论文）是目前最完整的公开实现。它的官方仓库给出的数字分两类：

指标数值口径
真实生产负载Kimi 在满足 SLO 前提下多处理 75% 请求项目方公开数据
长上下文模拟场景吞吐最高提升 525%论文模拟环境，非生产
40GB KV 数据传输（4×200Gbps RoCE）87 GB/sTransfer Engine 实测
同数据量（8×400Gbps RoCE）190 GB/s，比 TCP 快 2.4-4.6 倍Transfer Engine 实测

40GB 这个量不是随便选的，大致对应 LLaMA3-70B 在 128k 上下文下的 KV Cache。换句话说，长上下文能不能做、做得多贵，已经主要取决于跨节点搬这 40GB 要多久。网络与存储，第一次成了推理延迟公式里的主角。

2026 年的生态收敛，比单点性能更重要

判断一项系统工程是不是真成了，看有多少主流框架愿意为它改代码：Mooncake 2026 年 2 月加入 PyTorch 生态；vLLM、SGLang 把它作为分离式 prefill 的主要后端；LMDeploy、FastDeploy、llm-d、Dynamo 陆续合入；2026 年 10 月 TensorRT-LLM 在 KVCMv2 中合入原生 Mooncake Store connector，做内容寻址的跨实例前缀复用。这意味着 PD 分离不再是某家模型的私有优化，而是推理栈的默认选项之一。

内存介质这一层也在补齐：2026 年 3 月元脑 KOS 团队贡献代码，让 Mooncake 原生支持 CXL 单级存储；9 月中科曙光 ParaStor 成为首个接入的商用分布式存储后端。CXL 3.1 已进入量产，CXL 4.0（2025 年 11 月发布）把速率提到 128GT/s。腾讯等生产侧披露的口径（厂商新闻稿，非第三方审计）称 KV Cache 命中率最高 90%、长文本吞吐提升 6 倍、GPU 成本下降 30-40%。这些数字要打折看，但方向一致。

总结

「以存换算」是这轮推理架构变化最准确的概括：与其让每张 GPU 反复重算相同的前缀，不如用 DRAM、SSD 与 RDMA 网络把算过的结果存下来复用。对自建推理服务的团队，优先级应该重排——先看 KV 命中率与跨节点传输带宽，再看要不要加卡。在 128k 上下文成为标配之后，加卡的边际收益，很可能比不上一条 400Gbps 网络和一个设计得当的缓存池。

常见问题

什么是 PD 分离？

把 prefill（算力密集）与 decode（内存带宽密集）分到不同节点执行，通过分布式 KV Cache 池与 RDMA 传递中间状态，避免长 prompt 阻塞正在生成的请求，并让 KV Cache 不再独占单卡 HBM。

KV Cache 为什么值得单独优化？

它随上下文长度与并发数线性增长，是长上下文服务最先耗尽的资源；把热数据留在 HBM、冷数据下沉到 DRAM/SSD/CXL 池，并用前缀复用避免重复 prefill，能显著提升吞吐。

没有 RDMA 网络能做吗？

可以做但收益有限。Mooncake 的 Transfer Engine 在 8×400Gbps RoCE 下达到 190GB/s，比 TCP 快 2.4-4.6 倍；官方也明确建议在高速度 RDMA 环境下测试。
