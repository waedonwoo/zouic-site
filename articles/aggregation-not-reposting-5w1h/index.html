聚合不是转载：索引卡的内容边界要写在哪一层

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

ZouIC 首屏写着一句话：聚合 GitHub、Hackster.io、CrowdSupply、Hackaday、Seeed Studio 等平台的开源硬件项目，统一筛选与分页；所有项目仅供开发者参考，版权与授权归原作者，遵循其各自开源协议。这句话说得很清楚，但它是一句给人看的页面说明。一个聚合站真正要拍板的决定不在措辞，而在分层：数据层到底存了什么、结构化数据层把什么声明成主体、机器可读层又把哪些链接当成自己的内容推出去。只要其中一层越过界，首屏那句话就变成了单方面的愿望。下面按 5W1H 拆开。结论先说：索引卡是「关于项目的描述」，不是「项目的副本」；这条边界必须在四层里各写一次，而且四次要能互相印证。

何事 · What：被混淆的两种「内容」

聚合站生产的其实是两份东西。第一份是索引卡：项目名、一句话说明、来源平台、原链接、筛选标签、收录日期，以及站点自己写的归类与点评，这是站点原创的描述性内容。第二份是来源项目本身：仓库里的原理图、固件、BOM、README、教程正文、商品规格，版权与授权归原作者。混淆通常不是从抄袭开始的，而是从一次「为了搜索方便」的缓存开始的：把 README 全文抓下来存进自己的表，让站内搜索能命中；再把几张原理图存成本地图片，避免外链失效；接着为了让详情页显得完整，把教程正文也拼进去。每一步单独看都合理，四步之后，页面上那句「仅供开发者参考」已经描述不了实际发生的事。判断标准可以定得很朴素：站点能不能在删掉本地副本后，仅凭原链接把这张卡重新建起来。能，就还是索引；不能，就已经是转载。

何因 · Why：搜索引擎、机器读者与原作者要的不是同一句话

Google Search Central 的入门指南把话说得直白：内容要自己写、基于自己的认知，不要照搬或只是复述别人已发布的内容；它同时说明站内存在重复内容本身并不违反垃圾内容政策，但同样的信息出现在一堆不同地址上会造成体验问题并浪费抓取资源。规范化文档补了两条容易踩的细节：rel=canonical 是提示而非规则，平台仍可能另选规范网址；不要用 robots.txt 做规范化，被禁止抓取的地址仍可能被索引、只是不收录内容。于是三方诉求就分叉了：搜索引擎要判断这张卡是不是有独立价值、以及哪个地址算正主；机器读者要判断这段描述对应哪个真实项目、授权是什么；原作者要的是署名、原链接和协议不被改写。只写一句「版权归原作者」无法同时回答这三方，因为它们分别读的是页面可见文案、结构化数据和链接关系，而不是同一层。

何人 · Who：四方各管一段，一致性没人自动负责

来源平台决定项目页有什么、协议挂在哪、什么时候下架；原作者决定授权范围，且可能在不同平台用不同协议发布不同产物；站点运营者决定收录哪些字段、写多少自己的描述、把哪些链接写进机器可读清单；搜索引擎与 AI 客户端决定怎么理解这些标记。schema.org 的词汇定义正好把这四方的边界摆出来：sameAs 指向「能无歧义表明该条目身份」的参考页，isBasedOn 表示本作品由哪个资源衍生或改编（并已取代 isBasedOnUrl），license 指向适用于本内容的许可文档，citation 是对另一作品的引用，mainEntityOfPage 则说明某页以哪个东西为主体。这些字段不是装饰：把来源仓库的链接填进 sameAs，等于声明「这张卡和那个仓库是同一个身份」；填进 isBasedOn，等于声明「这张卡是那个项目的衍生作品」。两种声明对应的责任完全不同，而填错的成本要由站点承担，不由填字段的模板承担。

何时 · When：四个不同步的时间点

第一是收录时刻：站点抓取元数据、写下收录日期，这是唯一能证明「当时看到了什么」的时间点。第二是来源变更时刻：仓库改协议、归档、删库、商品页下架、教程被编辑，站点未必收到通知。第三是站点导出时刻：静态导出把当前卡片固化成 HTML，此后页面不再随源站变化，直到下次重导。第四是外部读取时刻：搜索引擎或机器客户端可能拿着几周前缓存的版本。把这四个时刻压成一个「当前状态」，是聚合站最常见的失真来源。工程上的对策不是实时同步——那会引入更多抓取与合规问题——而是把时间显式化：卡片写收录日期与最近核对日期，机器可读清单写基准日，失效与协议变更另行标注状态，并且让「最近核对」不等于「内容已核对无误」，只是「链接与字段在这一天被访问过」。Google 的规范化文档还提醒，不同语言版本只有在主要内容仍是同一语言时才算重复页，所以三语索引卡不能用一套 canonical 互相指来指去，得各自自引用并靠 hreflang 闭环。

何地 · Where：四层落点，缺一层就会被读成另一种站

数据层只该有元数据、原链接、来源平台、协议指向、收录与核对日期、站点自己的描述和标签；正文、原理图、固件与商品图留在原站，用链接引用。页面层把「版权与授权归原作者、遵循各自开源协议」写成可见说明，并把原链接做成可点的显眼出口，而不是藏在页脚。结构化数据层用 sameAs 指向权威身份页、isBasedOn 或 citation 表达衍生与引用、license 指向协议地址，主体的 mainEntityOfPage 指向本站这张卡，明确站点描述的是「关于项目的条目」而不是「项目本身」。机器可读层（sitemap、llms.txt 一类清单）只列本站页面地址，不把来源项目页混进本站清单冒充自家内容。四层的边界必须一致：任何一层出现了来源全文或把来源页列进本站清单，另外三层的说明就自动失效。站内做死链与 sitemap 校验时，也应分清「本站地址是否存在」和「外链是否还活着」，两者不是一次检查。

如何 · How：把边界做成四条可复核的断言

第一条，数据层断言：本地表里不存在来源项目的正文字段、设计文件二进制或图片副本；若确有缩略图，单独标注用途与来源，并允许一键清除。第二条，链接层断言：每张索引卡的来源链接可解析、指向原站而非本站镜像，且协议地址（若有）与卡片标注一致；原链接失效时进入待复核状态，不静默删除也不当作正常。第三条，标记层断言：sameAs 与 isBasedOn 不指向同一个 URL 表达同一件事，license 不与来源平台主页混用，三语卡各自自引用 canonical 并构成 hreflang 闭环。第四条，清单层断言：sitemap 与机器可读清单里出现的每个地址都属于本站域名，来源项目页只以链接形式出现在卡片里。四条断言都写进上线前自检，而不是写进编辑规范让人自觉遵守。做完这一步，再讨论要不要为来源做快照、要不要加摘要，讨论才有共同基线。

边界：这套拆法在哪里不成立

它解决的是「站点自己有没有越界」，不解决「来源本身是否授权清晰」。一个仓库可能把代码、原理图、文档分别挂在不同协议下，也可能根本没有许可证文件；此时站点写「遵循其各自开源协议」只是在转述，不能替原作者补全授权。schema.org 的字段是词汇定义，不保证任何搜索引擎都会读取或据此改判内容归属；rel=canonical 按平台文档只是提示，站点不能靠它强制指定身份。静态导出还带来一层滞后：页面是某个时刻的快照，机器读者拿到的可能是更早的缓存，两者都可能与今天的源站不同。更实际的缺口是，HTTP 层看不到内容被取走之后是否被用于索引、摘要或训练，声明与日志都只覆盖到交付当时。这些缺口不是加一个字段能补的，只能靠标注基准日、保留核对记录，以及遇到争议时以原作者页面为准。

结论：把「不是转载」写成结构，而不是写成表态

一句写在首屏的版权说明有价值，但它是表态；真正的边界是数据结构、链接关系、标记字段和清单范围共同构成的事实。建议把顺序倒过来：先决定本地不存什么，再决定卡片里放什么，然后补齐 sameAs、isBasedOn、license 与自引用 canonical，最后把四层一致性做成上线前的自动断言。这样即便将来要加全文摘要、要做离线快照，也会立刻撞上其中一条断言，迫使团队重新拍板，而不是在无人察觉的情况下把聚合站慢慢变成转载站。对读者而言这同样更省事：他能在一张卡上看到「这是什么、原站在哪、谁定的协议、我们什么时候核对过」，然后自己决定要不要点过去。

数据与口径（基准日 2026-11-13）：首屏文案「聚合 GitHub、Hackster.io、CrowdSupply、Hackaday、Seeed Studio 等平台；所有项目仅供开发者参考，版权与授权归原作者，遵循其各自开源协议」出自 ZouIC 首页 hero 的站点自身口径。sameAs、isBasedOn（取代 isBasedOnUrl）、license、citation、mainEntityOfPage 的词义出自 schema.org CreativeWork 与 SoftwareSourceCode 词汇定义，属规范文本口径。「重复内容本身不违反垃圾内容政策、内容需自己撰写、rel=canonical 是提示而非规则、不要用 robots.txt 做规范化、不同语言版本仅在主要内容同语言时才算重复」出自 Google Search Central 的入门指南与规范化文档，属平台官方口径。第三方 SEO 整理中关于「重复内容惩罚」的讨论与本文结论方向一致，只作辅助说明，不作为依据。规范词汇定义不等于搜索引擎的实际采纳行为，两者并列写出，不取平均。

常见问题

卡片里存了来源项目的 README 全文，还算聚合吗？

按本文采用的判断线，已经不是纯索引了。可复核的标准是：删掉本地副本后，能否仅凭原链接把卡片重建起来。若不能，就应当把它当作转载处理，明确授权与署名，而不是继续用「仅供开发者参考」描述。

sameAs 和 isBasedOn 都填来源链接，会有什么问题？

两者声明的关系不同：sameAs 表示身份一致，isBasedOn 表示本作品由该资源衍生。同一张卡若用两个字段指向同一 URL 表达同一件事，机器读者无法判断站点是在说「这是那个项目」还是「这是基于那个项目的作品」。按需选一个，其余用 citation 或普通链接。

把来源项目页也放进 sitemap，能让它们更快被收录吗？

不应该。sitemap 表达的是本站希望被抓取的地址集合，把别人的页面列进去既不改变归属，也会让清单口径失真。来源页应作为卡片里的可点链接存在；本站清单只列本站地址，这是四层一致性里最容易验证的一条。
