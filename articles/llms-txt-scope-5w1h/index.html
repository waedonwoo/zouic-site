llms.txt 该承诺多大范围：清单、全文与三语边界

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

把 llms.txt 理解成「给 AI 看的 sitemap」，是这份文件最流行的误读，也是随后一连串范围争议的起点。提案原文把自己的定位写得相当克制：一份放在站点根目录、供推理时按需读取的策展清单，唯一必需的部分只有一个 H1 项目名。至于那个被很多工具默认期待的 llms-full.txt，提案并没有定义它，它是文档平台自行形成的惯例。下面按 5W1H 把「该承诺多大范围」拆开。结论先说：清单要短而准，全文文件要先声明范围再给内容，三语版本宁可少收也不要混排；把没做到的事写成已做到，是机器可读层里代价最高的一种乐观。

何事 · What：四个文件，四种互不等价的范围

robots.txt 是 IETF RFC 9309 规范下的抓取指示，sitemap.xml 是尽量穷举的可发现 URL 清单，llms.txt 是提案意义上的精选入口清单，llms-full.txt 则是把正文拼接进一个文件的工具惯例。llmstxt.org 的现行文本规定了固定顺序：一个 H1 项目名（唯一必需段），一段 blockquote 摘要，若干不带标题的补充说明段，随后是若干个以 H2 分隔的文件列表，列表项必须含一个 Markdown 链接，可选用冒号补一句说明；名为 Optional 的段落有特别含义，里面的链接在需要更短上下文时可以跳过。提案还建议页面同时提供干净的 Markdown 副本，第二版增加了 rel="alternate" type="text/markdown" 与 rel="describedby" 两种链接关系。把这些摆在一起就能看出，穷举、策展、内联正文是三件事，任何一份文件都不自动覆盖另外两份的范围；把 llms-full.txt 当成「全站全文归档」来命名和宣传，本身就已经越过了提案的边界。

何因 · Why：范围含糊会被下游当成授权或完整性承诺

策展清单的价值在于替读者筛掉噪声，一旦它被读成「站点只有这些内容」或「这些内容可以任意使用」，性质就变了。提案明确说 llms.txt 不阻止任何人、不授予访问权、也不影响是否抓取站内其他路径；把某页从清单里拿掉不等于隐藏它，把某页列进去也不覆盖 robots.txt 的禁止规则。Google 的搜索指南（2026-07-10 更新）给的是另一种口径：不需要机器可读文件、AI 文本文件或 Markdown 也能出现在其搜索与 AI 特性里，保留 llms.txt 供其他服务使用无妨，但它既不帮助也不损害在该搜索里的可见度与排名。于是同一个文件，在搜索侧没有排名收益，在部分智能体工具侧会被当作入口地图，在审计工具侧只被当作「存在性」检查——Chrome Lighthouse 的实验性 Agentic Browsing 类别就只检查根路径有没有这个文件，不校验格式、链接，也不证明有任何 AI 系统读过它。三种读法并存，范围写得越含糊，被误当成承诺的概率越高。

何人 · Who：提案方、工具方与站点各管一段

提案由 Jeremy Howard 于 2024-09-03 提出，现行文本是维护在公开仓库里的社区提案，不是 IETF 或 W3C 标准，任何搜索引擎或模型提供方都没有义务读取它。文档平台与工具链把 llms-full.txt、llms-ctx.txt 等派生文件带成了事实惯例，其中由 Mintlify 与 Anthropic 协作推广的整站拼接用法最常被引用。站点运营者真正能控制的只有自己发布的这一份：写哪些链接、说明到什么粒度、覆盖哪些语言、多久更新一次。内容团队还要为译文负责——多语站点里，「有中文正文」和「有对应语种的正文」是两件事，把缺译文的中文塞进英文或德文文件，会让本语种的读者读到另一种语言，也会让基于语言的自动处理把语种判断错。责任划分上最容易漏的一环是：没有人负责在源内容变更之后，回头核对清单与全文文件是否还一致。

何时 · When：四个不同步的更新时刻

提案文本的更新时间是 2026-08-10（第二版），搜索平台指南的更新时间是 2026-07-10，文件本身的发布时刻由站点决定，而下游读取时刻完全不受站点控制。这四者不同步带来两个具体要求。一是清单里的链接必须指向当时确实存在、且返回 200 的地址，多语站点尤其要核对语言前缀派生出来的路径是否真的有产物，否则清单会变成死链清单。二是文件需要带上基准日或版本说明：正文篇数、栏目数、覆盖语种这类统计值会随内容更新变化，写死在文件里而不标日期，几个月后就会被读成过期但看似精确的承诺。同理，全文文件若只收录了部分文章，应当在文件头就写明范围与筛选规则，而不是让读者从内容里自己猜「大概还有别的没收」。

何地 · Where：站点级地图与页面级标记的分工

llms.txt 工作在站点级，回答「先读哪几个入口」；schema.org 的 JSON-LD 工作在页面级，回答「这一页是什么、谁提供、有没有价格、有哪些问答」。提案原文也提到文件可以引用站内使用的结构化数据，帮助读者在上下文中理解这些信息，两者是互补而非替代。落到目录结构上还有一层：文件默认位于根路径，也可放在子路径下，此时它覆盖的是该路径下的 URL，多个文件同时适用时应取最具体的一个；提案没有采用 /.well-known/，理由之一是共享主机上很多作者只能控制某个路径。多语站点通常会按语言前缀各出一份清单与全文文件，这时「范围」还要再加一维：本语种文件只列本语种确实存在的页面，不把其他语种的正文混排进来，也不因某个路径在别的语种存在就推定本语种也有。

如何 · How：把范围写成四句可验证的话

第一句写清单性质：这是策展入口，不是全站 URL 清单，完整可发现地址以 sitemap 为准。第二句写全文文件的范围：本次收录哪一类内容、共多少篇、按什么规则筛掉、有没有对应译文；没有译文的条目直接略过，并在文件头说明「不收录无本语种译文的内容」，而不是用原文补位。第三句写口径与时点：统计数字标注基准日，价格、篇数、栏目数都标清是站点自算还是外部数据，供应商自测与第三方整理分开写。第四句写更新与校验：清单链接逐一请求并确认 200，三语文件的可见文本做语种纯度检查，全文文件与源正文定期比对，且 robots.txt 不要 Disallow 这两个文件。四句话写进文件头，比在正文里反复解释更省事，也更容易被自动校验。

边界：这些文件证明不了什么

提案不是标准，无人有义务读取；即便被读取，也不构成授权、不构成完整性证明、不影响搜索排名。搜索平台与工具链的口径并不一致：一方明确说不需要这类文件，另一方把它做成存在性审计项，两者描述的是不同系统，不能合并成「AI 会读」这一个结论。全文文件还带来提案本身没有覆盖的问题：拼接后的体积、内容新鲜度，以及把不可信文本整段送进模型上下文时的注入风险，都属于工具方与站点的额外责任。多语版本更有一道硬边界——译文缺失是内容事实，不能靠文件结构掩盖；语种纯度检查若不剔除脚本、样式与注释，还会把代码里的字符串误判成正文。文件能表达的是站点主动声明的范围，表达不了下游是否真的按这个范围使用。

结论：宁可少承诺，不要假完整

把 llms.txt 当成一份带说明的推荐阅读清单来维护，链接少而准，每条写清这页回答什么问题；把 llms-full.txt 当成一份明确标注范围与基准日的选编，而不是全站归档；三语各守各的语种，缺译文就如实略过并在文件头说明。再补上两条纪律：结构化数据留在页面级，抓取偏好留在 robots.txt，别让一份 Markdown 承担四种职责。这样发布出去的文件，即便下游一个都没读，至少不会让读到的人形成错误预期；而一旦有人真的按它取数，站点也能拿出对得上的账。

数据与口径（基准日 2026-11-12）：文件格式、唯一必需段、Optional 段语义、Markdown 副本、第二版新增的两种链接关系、文件不阻止抓取且不覆盖 robots.txt，出自 llmstxt.org 提案现行文本（社区提案，页面标注第二版修改于 2026-08-10，最初提案发表于 2024-09-03）。Google 关于不需要机器可读文件、llms.txt 不影响其可见度与排名的表述，出自其搜索指南（第三方整理引述该指南 2026-07-10 更新）。llms-full.txt 由文档平台推广、提案未定义该文件名，以及 Chrome Lighthouse 实验性 Agentic Browsing 类别仅做存在性检查，来自第三方技术整理与工具文档，属工具方口径。提案方、搜索平台、工具方三者的描述并列写出，不合并为单一结论；实施前请核对各方当期文档。

常见问题

llms-full.txt 是 llms.txt 规范的一部分吗？

不是。提案定义了根路径下的 llms.txt 与页面 Markdown 副本，并没有定义 llms-full.txt 这个文件名；把站内正文拼接成一个文件是文档平台后来形成的惯例。发布时最好在文件头写明它是自定义产物及其收录范围。

把某页写进 llms.txt，等于允许抓取吗？

不等于。清单既不授权也不禁止，不影响 robots.txt 的规则，也不影响索引；把某页从清单里去掉同样不等于隐藏它。放行与封禁要在抓取规则、边缘策略或鉴权层单独决定。

多语站点里没有译文的文章该怎么处理？

本语种文件里直接略过，并在文件头说明「不收录无本语种译文的内容」。用中文原文补位会让该语种文件混入另一种语言，既影响读者，也会让基于语种的自动处理判断错误。
