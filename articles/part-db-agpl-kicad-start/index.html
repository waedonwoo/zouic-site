先管「我有什么」，再管「世上有什么」：Part-DB 给的起步顺序

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

「做一个开源元器件大数据平台」这句话里，最危险的是「大」。Part-DB 走的是反方向：先把工程师手上已有的几百个料号管清楚，再谈接外部数据源。这个顺序决定了项目能不能在半年内形成反馈回路。

它实际提供了什么

据 Part-DB 官方文档，这是一个部署在 Web 服务器上的开源元器件库存系统，基于 Symfony，后端可选 MySQL、MariaDB、PostgreSQL 或 SQLite，许可证为 AGPL-3.0。每个元件可归类目、封装、制造商、多个存放位置与价格，可挂数据手册与图片，支持参数化检索、条码标签与摄像头扫码；用户组有细粒度权限，可强制两步验证，也能通过 SAML 对接现有目录服务。

更关键的是闭环：可以导入 KiCad 项目的 BOM，直接算出「现有库存能装几套」并扣减元件；也能反过来作为 KiCad 的中央元件数据源，在设计软件里看到库存。外部参数、数据手册与价格通过 Octopart、Digikey、Farnell、LCSC、TME 等供应商按需获取，本地库始终是主数据，外部平台只是补全手段。官方提供 Docker 镜像，省掉 PHP 环境搭建。

库存优先的三个理由

这不是功能取舍，是数据质量的取舍：

  • 边界天然有限：全行业型号是无边界集合，永远做不完；自己货架上的料号是有限集，可以在一周内做到准确、可盘点、可验收。
  • 有真实的校验回路：每次导入 BOM、每次算「能装几套」，都在用实际项目检验数据。缺封装、少料号、单位写错会立刻暴露，而一个只供检索的大库没有这种反馈。
  • 许可证要提前算进商业计划：AGPL-3.0 意味着你若修改并对外提供网络服务，需以同许可证公开相应改动。这不是缺点，但把它当成 MIT 用，会在第一次谈商业合作时返工。

和商业平台不是替代关系

商业库解决「市场上有什么、谁家能替代、什么时候停产」，Part-DB 解决「我抽屉里有什么、这单 BOM 够不够」。把两者叠起来看，开源项目的合理站位很清楚：不复制 1.8 亿条手册，而是让工程师自己的 500 条记录准确、可追溯、能和设计与采购流程对接；需要外部数据时，通过可替换的适配器取，且保留原始出处与日期。

总结

先闭环，再扩面。一个能被 BOM 反复校验的小库，价值高于一份没人敢用的大清单；数据项目最稀缺的从来不是条目数，是有人愿意为它的准确性负责。

常见问题

Part-DB 用的是什么许可证？

GNU Affero GPL v3.0 或更高版本。修改后对外提供网络服务时，需要按同许可证公开相应改动；商业计划里应把这一条提前算进去。

它和商业元器件数据库有什么区别？

Part-DB 管的是自己手上的库存，支持条码、BOM 导入、参数检索与 KiCad 联动；商业库管的是全市场型号、替代关系、生命周期与行情。前者是主数据，外部供应商接口只是补全手段。

为什么建议从库存而不是从参数库起步？

库存是有限集，能快速做准确；每次 BOM 导入都形成真实校验，数据错误会立刻暴露。全行业型号无边界，缺少反馈回路，容易停在「条目很多但没人敢用」。
