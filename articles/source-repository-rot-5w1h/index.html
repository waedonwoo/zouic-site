来源仓库删了或归档了：索引卡留什么、标什么

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

做聚合站迟早会撞上这一天：一张收录了半年的项目卡，点开来源链接是 404。直觉反应是把死链清掉，让 sitemap 和校验重新变干净。但「清掉」这个动作同时抹掉了另一件事——站点曾经依据什么收录了这条项目、在哪一天核对过、后来发生了什么。GitHub 官方文档把上游状态分得很细：归档是只读且表明不再主动维护，删除是不可撤销且不一定影响已有 fork，公共内容还可能因合规原因被设为不可用。这些状态对索引卡的含义完全不同，却常被一个 available 字段压平。下面按 5W1H 拆开。结论先说：状态要有类型、有日期、有证据去向；清理动作针对的是「本站地址」，不是「外链记录」。

何事 · What：失效不是一个状态，至少是五个

按 GitHub Docs 的官方描述，归档仓库会对所有用户设为只读，用来表明不再主动维护；归档后议题、拉取请求、代码、wiki、版本、提交、分支与权限都变只读，但仍可搜索、可复刻、可标星，也能取消归档。删除则是另一回事：仓库删除不可撤销，部分已删除仓库在限定时间内可恢复，删除公共仓库不会删除它已有的公共 fork，平台会选一个现有 fork 作为新的父仓库让网络继续存在。此外还有三类常见变化：许可证文件被替换或新增，仓库从公开改为私有或反之，以及内容因 DMCA 通知或违反条款被设为不可用。把这五种变化都记成「链接打不开」，会直接导致两类错误：把仍可只读访问的归档项目误删，以及把已经改了协议的项目继续按旧协议标注。

何因 · Why：清理逻辑和证据逻辑的目标相反

静态站点的导出脚本天然偏向清理：站点自己生成的分页、旧版目录、多语派生路径都要定期修剪，否则产物会无限膨胀，sitemap 里还会出现指向不存在文件的地址。ZouIC 的导出链路里就有这类批量清理，并设了阈值保护，避免一次误删几十个目录；sitemap 生成也会主动排除并不存在的派生语言路径。这套逻辑只适用于「本站地址」。外链记录属于证据逻辑，目标是让后来的人能复盘：这条项目当时是什么、站点为什么收录、什么时候发现变化、有没有替代入口。两套逻辑混在一个「清理死链」的任务里，最常见的后果是导出成功后校验全绿，而收录依据永久消失。更麻烦的是机器可读层：如果 llms.txt 或清单里的范围说明写的是「本站当前收录」，那删掉失效卡是诚实的；若写的是「本站收录过并保留记录」，删掉就变成了承诺落空。

何人 · Who：上游、存档方、站点与读者各持一份

上游作者或维护者决定归档、删除、改协议、改可见性，通常不会通知下游聚合站。平台决定内容在什么条件下不可用，也提供长期保存机制：GitHub Docs 说明 GitHub Archive Program 默认纳入所有公共仓库，与 Software Heritage Foundation、Internet Archive 等机构合作，通过多种格式与位置保存副本；文档还建议添加开源许可证，因为明确的复制与分发权限会影响第三方是否愿意收录存档，仓库所有者可以退出该计划。站点决定保留多少状态、如何对外表述；读者需要的是「还能不能拿到、去哪拿、按什么协议拿」。四方持有的信息并不对称：平台知道删了什么，存档机构可能还有副本，站点只知道自己最后一次核对看到了什么。因此站点不该假装拥有全局视图，而应把自己那份如实写出来，并把「可能仍有镜像或 fork」写成提示而非保证。

何时 · When：核对日、变更发现日与导出日是三个日子

收录日说明项目首次进入索引的时间；最近核对日说明站点最后一次成功访问来源链接的日期，它只证明「那天链接与字段被访问过」，不证明内容无误；变更发现日说明站点第一次观察到状态变化的日期，这个日期通常晚于上游真实变更，滞后无法消除，只能标注。静态导出又是第四个时刻：页面固化成 HTML 后不会自动跟随上游，直到下一次重导。把这四个日子写进卡片与内部记录，争议时才有可追溯的序列。平台侧还有两个日历式事实值得单独记：删除后是否处于可恢复窗口，以及归档是否已被取消。它们决定了站点应该「暂标待复核」还是「改标恢复」。任何自动任务都不该仅凭一次请求失败就判定永久失效——网络抖动、限流、临时维护都会产生同样的现象，稳妥做法是连续多次、间隔观察，再改状态。

何地 · Where：状态落在卡片、记录、清单三处，措辞各不相同

卡片上给读者的是一句短状态加日期，例如「来源仓库已归档，仍可只读访问」或「来源链接不可达，最后核对于某日」，并保留原链接与协议指向；不写「本站已备份」「点此获取副本」这类会改写授权印象的措辞。内部记录存完整状态机：归档、删除、协议变更、可见性变更、设有替代入口、待复核、已恢复，以及每次观察的原始状态码与时间。机器可读清单与 sitemap 只列本站地址，所以外链失效不该触发「从 sitemap 删除本站卡片」；除非决定整张卡下线，那时才同时处理本站地址与清单范围。若站点确要提供镜像或存档引用，应当单独标注提供方与协议依据，不能与来源链接混为一谈。三处措辞不同但状态同源，靠一个内部状态字段驱动，避免卡片说归档、清单说下架、记录说 404。

如何 · How：把「留什么」写成六步状态流程

第一步，收录时落库：来源链接、平台、协议指向、收录日、站点自己的描述与标签，缺一不收。第二步，定期核对只取状态与协议文件的变化，不抓正文，避免把索引变成缓存。第三步，失败重试并分级：区分网络错误、404、403、重定向到不同域、页面仍在但许可证文件变了，不同结果进不同状态。第四步，观察期内标「待复核」，保留卡片与原链接，不静默删除也不当作正常。第五步，确认变化后按类型标注，并写清「归档不等于不可用」「删除不等于所有副本消失」「协议变更以变更后的文件为准，历史标注保留但标明失效日期」。第六步，导出前跑两条独立断言：本站地址无死链，外链状态字段完整且每个非正常状态都有日期与观察记录。把清理与保留拆成两个任务，校验报告里分别报数，才不会用一次全绿掩盖另一层的空白。

边界：这套状态机回答不了什么

它回答不了授权是否真的允许某种使用。归档只说明维护状态，不说明许可证是否仍有效；协议变更可能只影响后续版本，历史版本按什么授权需要看具体文件与提交记录，本文不替原作者作法律判断。平台存档计划是保存机制，不是站点可以据此再分发的授权，官方文档建议添加开源许可证正是因为这层区别；是否存在可访问的镜像或 fork，站点也只能提示，不能保证。技术上还有一层无法消除的滞后：静态页面、CDN 缓存与机器读者手里的旧版本，都可能与今天的源站不同。至于因合规原因被设为不可用的内容，站点更不应尝试绕过或重建。所有这类问题都应落到「以原作者与平台当期页面为准」这一句，并保留本站的核对记录作为事实，而不是作为结论。

结论：清理本站地址，保留外链证据

把两类动作彻底分开，是这件事最省力的解法。批量清理只处理站点自己生成的分页、旧版目录与派生路径，并保留阈值保护与「跳过保护要写原因」的记录；外链失效则进入状态机，带类型、日期、观察记录与替代入口提示，卡片继续可读但不再被表述为「当前可用」。状态机不需要复杂，七八个取值加三个日期就够，关键是别让一个布尔值替所有判断。这样哪天有人问「这条项目为什么还在站上」，答案不是「忘了删」，而是「来源仓库已归档，仍可只读访问，最后核对于某日，原链接保留」——一句能复核的话，比一次干净的全绿校验更有用。

数据与口径（基准日 2026-11-13）：归档仓库为只读、表明不再主动维护、议题与代码等变只读、可取消归档；删除不可撤销、部分已删除仓库可在限定时间内恢复、删除公共仓库不删除其公共 fork；公共仓库持续性及 DMCA 或违规情形下可能设为不可用；GitHub Archive Program 默认纳入公共仓库、与 Software Heritage Foundation 与 Internet Archive 等合作、建议添加开源许可证以便第三方存档、仓库可退出计划——以上均出自 GitHub Docs 官方文档，属平台官方口径。导出脚本的批量清理阈值保护、派生语言路径排除与 sitemap 死链校验，出自 ZouIC 自身工程记录，属站点自身口径。第三方关于链接失效与存档实践的经验整理只作方向性引用，不写进结论；平台存档机制不构成再分发授权，此处并列写出，不作推断。

常见问题

来源仓库归档了，是不是该把卡片下架？

通常不必。按 GitHub Docs，归档表示不再主动维护且变为只读，内容仍可搜索、复刻、标星访问。卡片应改标状态与日期，保留原链接，而不是当作失效删除。真正需要下架的是站点自己决定不再收录，那是另一个决定。

外链 404 了，为什么保留的卡片不算死链？

死链校验针对的是 sitemap 与清单里的本站地址；外链是卡片里的引用，不进本站 sitemap。保留它是为了留下收录依据与核对记录，但必须显式标注「不可达」与最后核对日期，不能让它看起来像正常可用的来源。

平台长期存档计划里有这个项目，站点能据此提供副本吗？

不能据此推断授权。GitHub Docs 把存档计划描述为保存机制，并建议项目添加开源许可证以便第三方收录存档；是否存在副本、能否分发，仍以原作者的许可证与平台当期页面为准。站点最多提示「可能存在镜像或 fork」，不提供副本、不作保证。
