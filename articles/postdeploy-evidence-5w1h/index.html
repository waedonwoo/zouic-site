发布之后留什么证据：线上复验该逐字比什么

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

一次发布之后，团队里常有人问「上去了吗」。最省事的回答是搜一下新文案、看几个页面返回 200。这两种做法都很快，也都不够：200 只能证明地址存在，关键词命中与否取决于你选了哪个词。项目里真实踩过一次——服务页上线后搜「会话存档」没有结果，一度以为整个企业微信区块没渲染；实际官方产品名是「会话内容存档」，而且导出后的 HTML 被压成单行，探针词和呈现形式都不对。后来改按区块锚点与正文主体核对，才发现七张产品卡与两类项目制产品一直都在。下面按 5W1H 拆开。结论先说：复验证据分三层，存在性、一致性、逐字一致；能逐字比就不要停在关键词。

何事 · What：三种证据强度，别混着用

最弱的是存在性证据：地址返回 200、关键文件能取回、sitemap 里出现了新条目。它回答「有没有」，不回答「是不是这一版」。中间是一致性证据：把若干探针（区块锚点、版本号、样式文件查询参数、结构化数据标记、语言标注、统计数字）与本地产物逐项核对，回答「像不像」。最强的是逐字一致：抽取线上页面与本地同路径产物的正文主体，去噪后做字符串比对，回答「是不是同一个内容」。三层各有成本，逐字比对最慢，但它能同时覆盖前面两层的多数问题，且不受探针词选错的影响。把三种证据混写成一句「复验通过」，等于允许最弱的一种替最强的那种背书。合理的做法是明确写出这次比了什么、比了多少页、结果如何，而不是只给一个结论。

何因 · Why：探针会骗人，缓存也会骗人

关键词复验有两个天然缺陷：一是命名会变，官方产品名、译文措辞、动态键渲染结果都可能与内部简称不同；二是 HTML 会被压缩、转义、注入脚本，肉眼可搜的字符串未必以预期形式出现。缓存则制造另一种误判：推送后立刻请求，拿到的可能是上一版页面，此时探针搜不到新文案是正常现象，不是部署失败。项目里的处理方式是等待部署窗口后带无缓存参数重取、检查响应头里的最后修改时间与缓存状态，再判断是「尚未生效」还是「确实错了」。GitHub Docs 关于自定义域名的文档也提示 DNS 变更传播可能需要较长时间，站点只能等待并复核。此外还有一层容易忽略：静态站点的产物是公开仓库内容，删除过的文件仍留在版本历史里，所以「线上还能访问到某个旧地址」未必说明本次部署漏删，也可能是历史副本仍在对外提供。

何人 · Who：发布者、托管平台与复验脚本各持一份事实

发布者持有提交号与本次改动范围，知道「应该出现什么」；托管平台持有构建与分发状态，知道「什么时候真正生效」；复验脚本持有外部视角，知道「这个请求实际返回了什么」。三方信息并不自动对齐，最常见的事故是发布者拿本地全绿当线上已生效。因此复验记录要能把三方串起来：提交号、部署等待时长、请求时刻与响应头、以及和哪一份本地产物比对。若由不同人执行发布与复验，还应把「预期变更清单」显式交给复验方，否则复验者只能凭印象挑探针，又回到关键词误判的老路。把责任分清之后，「上线了吗」这个问题才有明确归属：不是问平台，也不是问脚本，而是问那条能不能复核的证据链。

何时 · When：四个时刻决定一次复验是否有效

推送时刻给出提交号与改动清单；部署时刻由平台决定，站点只能观察；请求时刻决定拿到的是哪一版，必须与部署窗口对齐；比对时刻决定「本地产物」指的是哪份文件，若期间又有人改了源码或重新导出，比对的基准就漂了。项目里的做法是推送后留出部署窗口，再用带随机参数的请求取线上页面，同时记录响应头中的时间与缓存信息；必要时隔一段时间二次取样，确认不是撞上缓存切换的中间态。四个时刻里最容易被省掉的是「比对时刻」：很多人写「线上与本地一致」，却没说本地是哪一次导出的产物。一旦源码被并行改动，这句话就没有意义。把四个时间戳写进发布记录，比多跑几个探针更有价值。

何地 · Where：比正文，不比整页 HTML

整页 HTML 里混着运行时注入、脚本、样式、注释、统计代码与可能的缓存标记，逐字比几乎必然失败。项目采用的口径是抽取正文主体区域，去掉注释与脚本样式块后再比，这样既能覆盖「内容是否同一版」，又不会被无关差异淹没。具体落点分三处：文章页比正文主体与语言标注，服务与定价页比区块锚点与结构化数据，机器可读文本比整份纯文本内容（这类文件本就不该含脚本）。语言版本要分别取样，因为三语页面路径不同、导出映射不同；只比中文页会漏掉译文路径的问题。清单类文件还要单独比统计数字与基准日，它们常常不在任何页面的正文里，却是对外承诺的一部分。选对比对范围，逐字一致才既严格又稳定。

如何 · How：把复验写成六步，并留下记录

第一步，发布前固化预期变更清单：新增或修改了哪些地址、哪些文件、哪些数字与基准日。第二步，推送后记录提交号并开始等待部署窗口，不立刻下结论。第三步，带无缓存参数请求关键地址，记录状态码、响应头里的时间与缓存信息。第四步，跑线上自检清单，把结果与发布前的两次自检并列存档。第五步，抽样做逐字比对：从改动清单里挑若干代表页，抽取正文主体与本地同路径产物比对，语言版本分别取样；纯文本类文件整份比。第六步，写发布记录：四个时刻、比了哪些页、与哪份本地产物比、结果、以及任何未覆盖项。若某一步结果异常，先区分「尚未生效」「探针选错」「确实错了」三类，再决定是等待、换证据强度还是回滚；不要用一个失败的关键词直接触发回滚。

边界：逐字一致也证明不了什么

它证明不了事实准确、口径合理、第三方数字可靠，那些是内容审校的事。它证明不了外部平台如何解读标记与清单，也证明不了搜索结果或 AI 回答里会怎么呈现。它证明不了读者手里的版本：浏览器缓存、CDN 边缘节点与几周前抓走内容的机器客户端都可能持有更早的副本。抽样比对还有天然的覆盖上限，未被抽到的页面仍可能有问题，所以记录里要写明抽样范围而不是笼统写「全站一致」。最后，按 GitHub Docs 的提醒，公开仓库的产物内容本身是公开的、删除过的文件仍留在版本历史里，因此发布前还应有「产物里不该出现什么」的检查，例如密钥、内部路径与调试信息；这类风险与逐字一致无关，却同样属于发布证据的一部分。

结论：留一条能回答「和谁比过」的记录

「上去了吗」这个问题，值得一个比「搜到了」更结实的答案。建议把复验固定成三层：先看存在性，再核对探针一致性，最后抽样做正文逐字比对；每层写明比了什么、比了多少、与哪份本地产物比。四个时刻、提交号、响应头与抽样范围一并留档，异常时先分辨是缓存、探针还是真实缺陷。这样即便将来某天有人回看这次发布，也能从记录里复原当时的判断依据，而不是只看到一句没有主语的「复验通过」。顺便说一句，逐字一致这四个字之所以值得保留，是因为它把问题从「我觉得上了」换成了「这两份东西确实一样」。

数据与口径（基准日 2026-11-13）：线上服务页曾因用「会话存档」作探针搜不到内容、实际官方产品名为「会话内容存档」且导出 HTML 为压缩单行；线上复验包含声明生效、三语机器可读文本状态、自检项数、区块产品数量、样式版本参数、以及抽查若干文章三语正文与本地产物逐字一致；带无缓存参数重取与查看响应头时间、缓存状态——以上出自 ZouIC 自身发布记录，属站点自身口径。「自定义域名 DNS 变更传播可能需要较长时间」「Pages 仓库内容公开、删除文件仍留在版本历史」出自 GitHub Docs 官方文档，属平台官方口径。第三方关于 CDN 缓存与部署延迟的经验整理只作方向性引用，不写进结论；站点自检结果与平台行为并列写出，不互相替代。

常见问题

线上搜不到新文案，是不是可以直接判定没上线？

不能。先排除三种可能：部署窗口未到或缓存仍是旧版、探针词与官方命名或译文措辞不一致、HTML 被压缩或转义导致字符串形式不同。改用区块锚点、正文主体逐字比对，并核对响应头时间，再下结论。

为什么逐字比对只比正文主体，不比整页 HTML？

整页里有运行时注入、脚本、样式、注释与统计代码，这些差异与内容是否同一版无关，会让比对几乎必然失败。抽取正文主体并去掉注释与脚本样式块，既能覆盖内容一致性，又稳定；纯文本类文件则可以整份比。

抽样比对通过了，能写「全站一致」吗？

不建议。抽样天然有覆盖上限，未被抽到的页面仍可能有问题。记录里应写明抽样范围、与哪份本地产物比、四个时刻与结果，用「抽查若干页逐字一致」这类可复核的表述，而不是笼统的全站结论。
