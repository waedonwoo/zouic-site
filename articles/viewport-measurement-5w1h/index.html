390px 该信谁：截图宽度、CSS 像素与真机口径

算力行业观察 · 极客微栋 @GeekWaedon

极客微栋 @GeekWaedon · 2026 年 11 月

项目里做过一次移动端复核：把无头浏览器的窗口尺寸设成 390 宽，截图看起来满屏溢出，差点去改一版本来没问题的样式。后来发现浏览器把窗口钳到了更宽的值，裁出来的 390 只是图片宽度，不是页面实际布局宽度。改用强制设备像素比配合成倍窗口尺寸，再用页面内探针读一次真实值，才拿到可信的 390 CSS 像素。这类误判不来自 CSS 写错，而来自把四种不同的「宽度」当成同一个。下面按 5W1H 拆开。结论先说：截图只作视觉证据，不作宽度证据；任何移动端复核都要在页面内读一次实际值，并把测量口径写进记录。

何事 · What：四个都叫宽度的量

第一个是窗口参数，是给浏览器进程的启动值，可能被最小窗口尺寸、系统缩放或窗口管理器改写。第二个是 CSS 视口宽度，也就是布局与媒体查询真正使用的宽度，单位是 CSS 像素。第三个是物理像素，等于 CSS 像素乘以设备像素比，同一块屏在高密度下可以有成倍的物理像素。第四个是截图裁切宽度，只是输出图片的像素尺寸，与页面按多宽布局没有必然关系。MDN 的 viewport 文档把关键机制写得很清楚：width 在设置了 initial 或 maximum scale 时，实际表现为「最小视口宽度」，浏览器会在需要时扩展视口去填满屏幕；高密度屏上多个硬件像素对应一个 CSS 像素，devicePixelRatio 默认值随屏幕密度变化，且只有缩放为 1 时默认比例才成立；没有合适的 viewport 声明时，一些浏览器会采用约 980 CSS 像素的虚拟视口并缩放，导致窄屏媒体查询根本不生效。四个量混用，结论必然漂移。

何因 · Why：假破版和假通过都源自同一个错误

把窗口参数当 CSS 视口，会得到假破版：以为在 390 下溢出，其实页面按更宽布局，图片被裁窄后自然显得内容被切。反过来，把截图看着没问题当验证通过，会得到假通过：图片可能按设备像素比放大过、可能被缩放、也可能根本没触发目标断点。项目里的修复路径说明了这一点：不靠再调一次窗口参数去猜，而是在页面里放探针读 innerWidth 与 devicePixelRatio，必要时用固定宽度的 iframe 复测，把「当前布局宽度」变成一个可打印的数值。MDN 还提示了另外两类干扰：浏览器缩放会改变 CSS 视口宽度，虚拟键盘等交互组件也会改变视口，且可通过 interactive-widget 控制影响的是视觉视口还是布局。这些都说明，宽度不是启动参数能单独决定的常量，而是运行时状态。

何人 · Who：浏览器、页面、小程序与复核脚本各自说了算的部分

浏览器决定窗口钳制、缩放、虚拟视口与设备像素比；页面自己的 viewport 声明决定布局视口如何计算；小程序则完全是另一套体系，微信开放文档规定页面宽度统一为 750rpx，由平台按机型换算成实际尺寸，不能拿主站的 CSS 像素值直接套用。复核脚本决定取样方式：是读页面内探针，还是只看输出图片；人工复核者决定有没有把「看着像」当成「量过了」。四方里唯一能给出权威数值的是页面内探针，因为它读的就是布局实际使用的 CSS 像素。把这层分清后，讨论就会从「截图看起来对不对」变成「这次测量的对象是什么、谁测的、数值多少」——这才是能写进验证记录的话。

何时 · When：三个取样时刻，缺一个就可能误判

第一是页面加载完成时：此时布局视口已确定，适合读 innerWidth 与 devicePixelRatio。第二是字体、图片与脚本执行稳定之后：异步内容可能改变滚动宽度或触发横向溢出，过早截图会漏掉真实破版。第三是交互状态改变之后：虚拟键盘弹出、旋转屏幕、缩放变化都会改变视口，若要验这些场景就得单独取样。项目里用虚拟时间预算等待渲染稳定，再做整页截图与局部裁剪，正是为了把前两个时刻分开。缓存与版本也构成时间维度：截图对应的到底是哪一版页面，记录里要能追溯到提交号或导出批次，否则同一张图过几天就无法解释。把三个时刻与目标版本一起写进记录，比保存一堆没有元数据的图片有用得多。

何地 · Where：数值落在记录，图片落在附件，结论落在断点

验证记录里应写：目标 CSS 视口宽度、实际读到的 innerWidth、devicePixelRatio、窗口启动参数、缩放设置、页面版本，以及取样时刻；这些是可复核的数值。截图只作为视觉附件，用于看有没有重叠、错位、溢出，不承担证明宽度的职责。结论则落在断点上：目标宽度下哪些媒体查询生效、布局是否单列、导航是否折叠、有没有横向滚动。多端场景要分开记：主站按 CSS 像素与媒体查询，小程序按 rpx 与平台换算，两套记录不互相引用数值。若用 iframe 固定宽度做探针，也要注明这是「容器内宽度」而非浏览器窗口宽度，避免下一个人把两者等同。三层分开，截图才不会被误当成测量报告。

如何 · How：把移动端复核做成五步，且每步留数

第一步，明确目标值：要验的是哪个 CSS 视口宽度、对应哪个断点，而不是「手机大概多宽」。第二步，用能产生目标 CSS 宽度的方式启动浏览器：必要时用强制设备像素比配合成倍窗口尺寸，或改用固定宽度 iframe，别指望窗口参数等于布局宽度。第三步，页面内探针打印 innerWidth、devicePixelRatio 与滚动宽度，确认实际值与目标值一致，不一致就先修测量方式，不改样式。第四步，等渲染稳定后再截图，检查重叠、溢出与折叠；交互场景另行取样。第五步，写记录：目标值、实际值、启动参数、缩放、页面版本、取样时刻、截图路径与结论。若某一步发现破版，先确认不是测量误差，再动 CSS。这五步的核心不是工具，而是把「我看到了」换成「我量到了多少、按什么口径量的」。

边界：量准了也不等于真机没问题

无头浏览器量到 390 CSS 像素，只能说明这次布局宽度符合目标；它复现不了真机的字体渲染、系统缩放、浏览器界面占用、刘海与安全区、触摸目标手感，也复现不了不同厂商对 viewport 与虚拟键盘的细微差异。MDN 文档本身就把 interactive-widget 的三种取值列为不同行为，说明视口变化还有交互维度。小程序的 rpx 体系更是平台负责换算，桌面浏览器里的模拟值不能替代平台内的实际表现。因此这类复核应定位为「排除测量误差后的布局检查」，真机预览与设备上取样仍是独立环节。此外，截图只能覆盖被截取的可视区域，长页面下半部分的破版要靠加高视口或分段取样，不能凭上半部分正常推断整页正常。

结论：把测量口径写进验证记录

移动端复核最值钱的不是那张截图，是截图旁边那行数：目标多少、实际多少、按什么方式测的、测的是哪一版。项目里那次「390 满屏溢出」的虚惊，代价只是多跑一轮；如果当时直接按假破版改了样式，真正的断点问题反而会被掩盖。建议把探针打印、等待渲染稳定、数值与图片分开归档、结论落在断点这四件事固定成流程，并把主站 CSS 像素与小程序 rpx 明确分成两套口径。这样下次有人说「手机上看不对」，第一句回答就不是「我这边截图是好的」，而是「先报一下你量到的 innerWidth」。

数据与口径（基准日 2026-11-13）：无头浏览器把 390 窗口参数钳到更宽值、裁出的 390 只是图片宽度、改用强制设备像素比配合成倍窗口尺寸并以页面内 iframe 探针复核，出自 ZouIC 自身视觉复核记录，属站点自身口径。width 在设置 initial / maximum scale 时表现为最小视口宽度、浏览器可扩展视口填满屏幕、CSS 像素与硬件像素通过 devicePixelRatio 换算、默认像素比随屏幕密度分档且仅缩放为 1 时成立、缺失 viewport 声明时约 980 CSS 像素虚拟视口、interactive-widget 的三种取值，以及规范出处 CSS Viewport Module Level 1，均出自 MDN Web Docs 的 viewport 文档，属权威文档与规范口径。rpx 以 750rpx 为页面宽度基准、由平台换算，出自微信开放文档，属平台官方口径。第三方视口检测工具与断点经验文章只作方向性引用，不写进结论；浏览器模拟值与真机表现并列写出，不互相替代。

常见问题

把浏览器窗口设成 390，为什么布局不是 390？

窗口参数只是启动值，可能被最小窗口尺寸与系统缩放改写；若页面设置了 initial 或 maximum scale，MDN 说明 width 实际表现为最小视口宽度，浏览器还可能扩展视口。要以页面内探针读到的 innerWidth 为准。

截图看着没溢出，能算移动端验证通过吗？

不能单独算。截图可能被设备像素比放大或缩放，也可能根本没触发目标断点。应先打印实际 CSS 视口宽度与 devicePixelRatio，确认量对了，再让截图承担「看重叠、错位、溢出」的视觉职责。

主站量到 390 CSS 像素，能直接推断小程序的表现吗？

不能。小程序按 rpx 体系由平台换算，页面宽度基准是 750rpx，与主站的 CSS 像素和媒体查询不是同一套口径。两端应分别取样、分别记录，数值不互相引用；真机预览仍是独立环节。
